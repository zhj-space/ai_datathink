## 3. M0 第 6 项实测（流式首 token）

**方法**：`POST /api/generate`（`stream: true`），记录**从请求发出到收到第一个非空 `response` 分片**的耗时；`num_predict=64`。**长上下文 prompt 为 10,394 字符 ≈ 5.2k tokens**（模拟 RAG 检索上下文）。

| 模型 | 场景 | 首 token | decode | 判据（<10s） |
|---|---|---|---|---|
| qwen2.5:3b | 冷启动 · 短 prompt | 2.57 s | 16.5 tok/s | ✅ |
| qwen2.5:3b | 热态 · 短 prompt | **0.08 s** | 16.8 tok/s | ✅ |
| **qwen2.5:3b** | **热态 · 长上下文（首次）** | **12.61 s** | 13.9 tok/s | ❌ **不通过** |
| qwen2.5:3b | 热态 · 长上下文（复测） | 0.10 s | 14.5 tok/s | ✅（见下方口径提示） |
| qwen2.5:1.5b | 冷启动 · 短 prompt | 1.61 s | 31.4 tok/s | ✅ |
| qwen2.5:1.5b | 热态 · 短 prompt | **0.02 s** | 31.5 tok/s | ✅ |
| **qwen2.5:1.5b** | **热态 · 长上下文（首次）** | **6.55 s** | 26.2 tok/s | ✅ **通过**（余量不足 1/3） |
| qwen2.5:1.5b | 热态 · 长上下文（复测） | 0.08 s | 26.2 tok/s | ✅（同上） |

### 3.1 口径提示（**这条决定判读正确与否**）

**复测的 0.08~0.10 s 不代表真实 RAG 性能**：Ollama 会**复用已处理的 prompt cache**，同一 prompt 的第二次请求几乎不消耗 prefill 时间。**门禁判读应以"首次处理该上下文"的数值为准**（即 3b 12.61 s / 1.5b 6.55 s）。

### 3.2 结论

| 档位 | 判据结果 | 说明 |
|---|---|---|
| **qwen2.5:1.5b** | **通过** | 首次长上下文 6.55 s < 10 s（但余量仅 3.45 s，**上下文再长会越线**） |
| **qwen2.5:3b** | **不通过** | 首次长上下文 12.61 s > 10 s；短 prompt 场景通过 |
| 冷启动 | 双档均通过 | 3b 2.57 s / 1.5b 1.61 s（模型加载后首 token） |

> **采样声明**：以上为**单次采样实测**（工程经验数据，**需多次采样校准**）；prefill 耗时随上下文长度近似线性增长，故 **10s 门禁实际取决于"RAG 上下文预算"**，建议在 S4-2 明确该预算后再定判读口径。

### 3.3 口径更正（2026-09-19，**必读**）

| 项 | 原记录（v1.0） | 实测更正 |
|---|---|---|
| 长上下文样本的**实际 token 数** | "≈5.2k tokens（10,394 字符）" | **实际只有 2050 tokens**——Ollama **默认 `num_ctx` 上限 2050**，超出部分被**静默截断**（不报错、不提示）。实测：8,158 字符与 24,558 字符的 prompt，`prompt_eval_count` **都恰好是 2050** |
| 换算比（本平台文档格式：中文描述 + 英文 FQN） | 按 ~2 字符/token 估 | 实测 **1.70 字符/token**（1,622 字符 → 952 tokens）；保守取 **1.5** 用于预算裁剪 |
| 门禁结论是否改变 | 3b 不通过 / 1.5b 通过 | **结论不变，但口径收窄**：两组数值都是"**2050 tokens 上下文**"下的首 token（3b 12.61 s / 1.5b 6.55 s）。**不能再把它当作 5.2k tokens 的成绩** |
| 因此新增的硬要求 | —— | ① 必须显式设 `num_ctx`（S4-2 已设 **4096**）；② 必须给上下文设预算（S4-2 已定 **3000 tokens**）——否则"10s 门禁"没有稳定口径 |

> **复测（新口径，2026-09-19）**：预算内 prompt（4,341 字符，估算 2,889 / **实测 2,491 tokens**，`num_ctx=4096`）流式**首 token**：
> **冷启动 7.01 s ✅**、热态 0.04 s（热态含 prompt cache 失真，按 §3.1 口径不作判读依据）。
> 单次采样，**不能替代 M0 门禁的人工判读**。

### 3.4 3b 复测（新口径）+ **1.5b 余量警示**（2026-09-19，多次采样）

**方法**：与 M0 第 6 项同口径（`POST /api/generate`，`stream:true`，记录首个非空 `response` 分片的耗时），
`num_ctx=4096`、`num_predict=256`；**每个样本用不同的上下文（不同批次文档）**，避免 Ollama **prompt cache** 把复测测成假快（§3.1 的坑）。
预算内上下文为 12 篇合成文档，估算 2,751 / **实测 `prompt_eval_count` 2,847 tokens**。

| 模型 | 冷启动 · 预算内 | 热态 · 预算内（2 次） | 热态 · 短 prompt | decode | 模型体积 |
|---|---|---|---|---|---|
| **qwen2.5:3b** | **20.68 s ❌** | **17.30 s / 17.41 s ❌** | 0.20 s ✅ | 14.9~15.4 tok/s | 1,840 MB |
| **qwen2.5:1.5b** | **11.31 s ❌** | **8.39 s / 8.29 s ⚠️（余量仅 1.7 s）** | 0.11 s ✅ | 26.8~27.0 tok/s | 940 MB |

**结论（两条，第二条比第一条更重要）**：

1. **3b 在新口径下明确不通过**：预算内首 token **17~21 s**，是门禁（<10 s）的两倍以上；慢在 **prefill**（短 prompt 仅 0.2 s），
   与本机 CPU 档位（4.1.3：本环境"不适合验证准确率"）一致 ⇒ 若坚持 3b，只剩**触发 GPU 评估**一条路。
2. ⚠️ **1.5b 在 3,000 tokens 预算下也已贴线**：热态 8.3 s（余量 1.7 s）、**冷启动 11.31 s（越线）**。
   我在 §3.3 记的 7.01 s 是**单次乐观样本**（同口径复测波动可达数秒）⇒ **"1.5b 通过"的前提是"上下文 ≤ 约 2,000~2,500 tokens"，不是 3,000**。
   即：**B 项把预算定为 3,000，客观上把 1.5b 推到了门禁边缘**（该口径属工程取值，判读与定档**属人工专属**）。

**质量样例（走生产 RAG 链，真实上下文仅 194 tokens，单次样例，不构成准确率判读）**：

| 模型 | 正例（平台有哪些资产/属于哪个服务） | 负例（问不存在的表） | 耗时 |
|---|---|---|---|
| qwen2.5:3b | "…没有具体列出…答案是「元数据中未找到」；根据元数据，该资产属于 airflow_poc 服务"（**啰嗦、前后矛盾**） | "元数据中未找到" ✅ | 7.37 s / 4.34 s |
| qwen2.5:1.5b | "平台中的数据资产属于服务 airflow_poc"（**简洁准确**） | "元数据中未找到。" ✅ | 3.02 s / 2.71 s |

> 两者都能守住"不编造"底线；**3b 在本环境未见质量优势**（内存翻倍、速度减半、回答更啰嗦）。
> **本环境按 4.1.3 不能判读准确率**，上表只是样例。

**人工决策结果（2026-09-19，已执行）**：**档位取 1.5b + 压低上下文预算**。取值按事先定死的判据（**冷启动首 token < 8.0 s**，对 10 s 门禁留 20% 余量）实测比选：

| 预算 | 实际 prompt tokens | 冷启动首 token | 热态首 token | 采用篇数 |
|---|---|---|---|---|
| 1,500 | 1,576 | 6.88 s | 4.64 s | 6/12 |
| **1,800（已采用）** | **1,819** | **6.93 s** | **4.85 s** | **7/12** |
| 2,000 | 2,062 | 7.70 s | 5.66 s | 8/12 |

⇒ 取 **1,800**（范围内余量最充足；2,000 亦达标，留作接源后上调备选）。落地见《…S4-2…》§7 与 v1.5；
**未采用**"保持 3,000 + 延长 keep_alive"方案（会与 `OllamaModelNotUnloading` 规则口径冲突，且模型需长期驻留内存）。

## 7. 运行面告警与可观测性（2026-09-19 补，C 项）

### 7.1 问题：Ollama 此前**完全不可观测**

| 通道 | 实测结果 |
|---|---|
| Ollama 自带 `/metrics` | **404**（0.34.2 无 Prometheus 端点） |
| Prometheus 抓取目标 | **ollama = 0** |
| cAdvisor（本环境已容器化） | ⚠️ **只有根 cgroup**：逐容器序列为空。根因：Docker **29.8.1** 用 **containerd 镜像存储**（`io.containerd.snapshotter.v1`），`/var/lib/docker/image/overlayfs/layerdb/mounts/` **为空**（`mount-id` 计数 = 0），而 cAdvisor 是 **v0.45.0（2022-09-23）**，日志持续报 `failed to identify the read-write layer ID …` ⇒ **「抓取目标 up」≠「有数据」** |

> 结论：S4-1 的纪律「不得拖慢实时告警链路」**此前没有任何可执行的可观测手段**。cAdvisor 的修复属组件版本变更（需人工批准 + 重扫），本次**不擅自更换**。

### 7.2 落地：探针 + 7 条规则（不新增组件）

| 项 | 内容 |
|---|---|
| 采集 | `/data/ai-governance/scripts/ollama_probe.sh`（仓库 `alerting/ollama_probe.sh`，sha256 `6f565955…`）→ node_exporter **textfile** 独立文件 `ai_governance_ollama_runtime.prom` |
| 数据源 | **`GET /api/ps`**（仅回环）——**容器级 CPU/内存/OOM 指标已于同日移交通用探针 `container_probe.sh`**（全容器 cgroup v2，见 `alerting/README.md`）：**同一 series 只能有一个生产者**，否则同一序列重复采样会让 Prometheus 抓取直接失败 |
| 调度 | cron `/etc/cron.d/ai-governance-ollama` **每分钟**（独立文件，不动既有 cron） |
| 规则 | `ollama-runtime` 组 7 条：API 不可达(critical) / CPU 饱和(warning) / 内存高(warning) / **OOM kill**(critical) / 模型不卸载(warning) / 探针停摆(warning) / 指标整体缺失(warning) |
| 阈值口径 | CPU 80% / 内存 85% **沿用 S1-7 的 SLO 阈值**，分母取**容器自身 cgroup 限额**（实测 8.0000 核 / 16 GiB），非宿主 ⇒ **不新增臆造数值** |
