# AI 数据治理平台实施执行计划 v1.1

> 依据：本计划基于 [AI数据治理平台设计方案.md](./AI数据治理平台设计方案.md)（v3.0，开源单机优先版）第7章路线图拆解而成，聚焦"谁在什么时候做什么、需要什么资源"，架构/组件选型请以设计方案为唯一权威来源，本文档不重复贴组件表。默认部署路径为单机 Docker Compose（3节点 k3s 为规模化后的可选升级路径），实时链路采用 Flink CDC 直连捕获，无需独立部署 Kafka Connect/Debezium。
> 节奏说明：周数为**建议节奏**，用于资源排期参考；实际推进以设计方案"结果/门禁驱动"原则为准——门槛未达标不进入下一阶段，也不因为到了预定周数就强行推进。
> 执行方说明：v1.1 起，每项任务标注**执行方**（Agent 自主执行 / Agent 起草+人工审核 / 人工专属），可直接把本计划交给 AI Agent 按"执行方"分工接手技术性任务；人工判断/审批类任务的边界见第7章"Agent 执行边界与安全护栏"，不可越界自动化。

## 2. 资源需求总览

| DE | 1~2 人 | Phase 1/2 全职，其余阶段维护 | OpenMetadata、Airflow、Kafka、Flink、SQL |
| AI | 1 人 | Phase 3 全职 | LLM 部署、RAG、Prompt 工程 |

### 2.4 成本构成要素（不给具体金额，按类别列出供采购测算）

- 硬件：3 台服务器（或等效云主机）一次性/按月成本；GPU（若引入）
- 人力：按 2.1 团队规模 × 阶段周期估算人天
- 对象存储/带宽（若引入湖仓或异地备份）
- 外部咨询：法务复核（按需，通常一次性）
- 以上均为纯开源组件，**无软件许可费**，成本主要在硬件与人力

## 3. 分阶段执行计划（周粒度任务分解）

### Phase 0：基础设施与安全底座（建议 2~3 周）

| 周 | 任务 | 负责人 | 执行方 |
|---|---|---|---|
| 第1周 | 服务器到位、基础 OS/网络配置；默认路径安装 Docker+Docker Compose（单机）；若根据6.1决策直接从3节点 k3s 起步，则改为3台服务器安装 k3s 集群（`--cluster-init` + join）并验证 etcd 3 副本健康 | INFRA | 服务器到位/网络为人工专属；安装脚本编写与执行、验证为 Agent 自主执行 |
| 第2周 | 单机路径：部署 PostgreSQL+pgvector、OpenSearch（docker-compose）；3节点路径：配置 Helm 仓库，安装 CloudNativePG/Strimzi/OpenSearch Kubernetes Operator/Flink Kubernetes Operator/MetalLB，部署 PostgreSQL+pgvector 与 OpenSearch 集群 | INFRA、DBA | Agent 自主执行（生成 compose/Helm values 并应用，产出部署报告供人工审阅） |
| 第3周 | 监控上线（单机：Prometheus+Alertmanager容器；3节点：kube-prometheus-stack）；Traefik 入口验证；编写备份脚本并完成一次恢复演练；若为3节点路径，**额外模拟单节点故障验证自动故障转移生效** | INFRA、DBA、QA | 监控/入口部署与备份脚本编写为 Agent 自主执行；恢复演练结果验证为人工专属（DBA 需亲自确认数据完整性并签字）；故障注入为 Agent 自主执行，恢复结果由人工确认 |

**关键决策点**：默认从单机 Docker Compose 起步（见设计方案 6.1）；仅当验证通过且确实需要容忍单节点故障的高可用能力时，才升级到 3 节点 k3s（决策人：ARCH+PM）。若测试环境资源有限，直接按 4.1.3 最小测试环境规格评估，不建议直接搭 3 节点。
**准出门槛**：单机：所有容器健康检查通过；备份脚本验证可恢复。若选 3 节点：集群 3 节点均 Ready；模拟单节点故障验证自动故障转移生效；备份脚本验证可恢复。

### Phase 1：离线治理闭环（建议 3~4 周）

| 周 | 任务 | 负责人 | 执行方 |
|---|---|---|---|
| 第1周 | OpenMetadata Helm 部署；接入第 1 个核心业务源（schema/血缘抽取） | DE | Helm 部署为 Agent 自主执行；业务源连接器配置为 Agent 起草+人工审核（数据库凭证/访问范围必须人工确认） |
| 第2周 | 接入第 2 个业务源；sqllineage 补充复杂 SQL 解析；Presidio 批量扫描规则配置（含中国身份证/手机号自定义识别器） | DE、SEC | 业务源接入为 Agent 起草+人工审核；Presidio 自定义规则为 Agent 起草+人工审核（准确率必须人工验证后才能上线） |
| 第3周 | 置信度分层规则调优（高/中/低置信处理路径）；OPA 基础访问策略编写；人工复核队列跑通 | SEC、GOV | 规则调优、OPA 策略编写均为 Agent 起草+人工审核（防越权）；人工复核为人工专属 |
| 第4周 | Superset 基础治理看板搭建（资产覆盖率、质量趋势）；试点数据源验收 | DE、GOV、QA | 看板搭建为 Agent 自主执行；准出门槛验收为人工专属 |

**关键决策点**：Presidio 自定义识别规则抽检准确率是否达标，未达标需评估是否要迭代规则或调整置信度阈值（决策人：SEC+GOV）。
**准出门槛**：试点数据源资产目录覆盖率 100%；敏感字段识别人工抽检准确率达标（如 >90%）。

### Phase 2：实时链路引入（建议 3~4 周）

| 周 | 任务 | 负责人 | 执行方 |
|---|---|---|---|
| 第1周 | Flink CDC 直连接入试点业务库（无需独立 Kafka Connect）；Kafka Topic 规划（分区数/副本因子对齐 Flink 并行度） | DE、DBA | CDC 接入涉及生产源库权限，为 Agent 起草配置+DBA 审批后 Agent 执行；Topic 规划为 Agent 自主执行 |
| 第2周 | Flink 作业开发（流式规则引擎 + OpenLineage 实时血缘事件），部署到 Flink Kubernetes Operator | DE、ARCH | 作业开发与部署为 Agent 自主执行；规则逻辑上线前需人工审核 |
| 第3周 | Governance Agent 告警增强模块开发；Alertmanager/IM 告警打通 | DE | Agent 自主执行 |
| 第4周 | 端到端压测（P95 延迟）；连续运行观察，验证无未恢复故障 | QA、DE | 压测脚本与数据采集为 Agent 自主执行；是否达标的判读为人工专属 |

**关键决策点**：CDC 对源库负载是否可接受，需 DBA 与源系统负责人共同评估签字后才可扩大接入范围。
**准出门槛**：端到端延迟 P95 < 30 秒；连续运行 1 周无未恢复故障。

### Phase 3：AI 能力增强（建议 3~4 周）

| 周 | 任务 | 负责人 | 执行方 |
|---|---|---|---|

**准出门槛**：问答准确率与引用可核验率抽样达标；人工复核吞吐量在置信度分层后可控。

## 6. 沟通与汇报机制

- **周例会**（15~30 分钟）：各角色同步进度、暴露阻塞项，PM 主持。
- **阶段门禁评审会**：每个 Phase 结束前，PM 组织 ARCH/相关角色共同确认准出门槛是否达标，形成书面记录后再进入下一阶段。
- **月度汇报**：向管理层汇报整体进度、风险状态、资源使用情况。

## 7. Agent 执行边界与安全护栏

明确"哪些交给 Agent 自主执行、哪些必须暂停等人工确认"，避免自动化越界；对应各阶段任务表的"执行方"列。

### 7.1 Agent 可自主执行的任务类型

- 基础设施即代码：k3s 安装脚本、Helm values、K8s manifests/CR 的编写与应用
- 幂等、可重复、失败可重来的部署/配置操作
- 测试类脚本的编写与执行（压测脚本、故障注入脚本、备份恢复脚本本身）
- 文档/报告生成（部署报告、压测报告、准出门槛核对清单）
- 基于已批准规则的重复性数据处理（如按已确认的 Presidio 规则批量扫描）

### 7.2 Agent 必须暂停、等待人工确认的场景

- 涉及生产源业务数据库的权限申请与首次连接（CDC 接入前必须 DBA 审批）
- 任何"删除、清空、reset、force"类操作，或影响生产数据/集群的不可逆变更
- PII 识别规则、OPA 访问策略首次上线前（Agent 可起草，人工必须审核准确率/越权风险后再启用）
- 涉及金额/许可证的决策（如引入 Grafana/Dify 需 LEGAL 复核）
- 所有"准出门槛"的最终判定（Agent 可提供数据，但门槛是否达标由人工确认）
- 硬件采购、物理机架、网络防火墙策略这类物理/组织流程

### 7.3 Agent 执行所需的前置条件

- 对 3 台服务器/k3s 集群的 SSH 或 kubectl 访问权限（按最小权限原则授予，避免长期使用管理员凭证）
- 代码仓库写权限（产出 IaC/Helm values 以 PR 形式提交，而非直接改生产）
- 以本设计方案与本执行计划为唯一依据，禁止臆造未在文档中出现的组件或参数
- 关键操作前默认 dry-run/plan 模式预览变更，人工确认后再实际执行（对应 kubectl 的 `--dry-run`、Helm 的 `--dry-run`、Terraform 的 `plan` 等）

### 7.4 人机协作节奏

- Agent 完成一个任务后产出：变更内容摘要 + 验证结果 + 是否需要人工确认下一步
- 人工在阶段门禁评审会（见第6章）上统一确认所有 Agent 产出是否可以进入下一阶段
- 出现 Agent 无法自主判断的分支（如报错、意外状态）时，Agent 应停止并上报，而非自行猜测继续执行

## 8. Agent 任务卡示例（以 Phase 0 为例，其余阶段可参照此格式扩展）

### 任务卡 P0-1：搭建 k3s 三节点集群

- **前置条件**：3 台服务器已完成基础 OS 安装、SSH 可达、内网互通（人工确认后触发）
- **输入**：3 台服务器 IP/主机名清单
- **执行步骤**：① 第一台执行 `k3s server --cluster-init`；② 其余两台以 `K3S_URL`+`K3S_TOKEN` 方式 join；③ 执行 `kubectl get nodes` 验证
- **验收标准（可编程校验）**：`kubectl get nodes` 输出 3 个节点且状态均为 `Ready`
- **失败处理**：任一节点 join 失败，Agent 记录日志并停止，不自动重试超过 3 次，转人工排查
- **人工确认点**：集群搭建完成后，人工确认再继续下一任务卡

### 任务卡 P0-2：部署 PostgreSQL 高可用集群（CloudNativePG）

- **前置条件**：k3s 集群 Ready；Helm 仓库已配置
- **执行步骤**：① 安装 CloudNativePG Operator；② 编写 `Cluster` CR（1 主 2 从）；③ 应用并等待 Ready
- **验收标准**：`kubectl get cluster` 显示 3 实例、1 primary+2 replica 均健康
- **人工确认点**：首次创建的数据库密码/连接凭证需人工从 Secret 中安全获取并妥善保存，Agent 不得将其明文输出到日志

### 任务卡 P0-3：故障转移演练

- **前置条件**：P0-1、P0-2 已完成
- **执行步骤**：① Agent 选择一个非当前 leader 的节点，模拟宕机（如 `kubectl drain` 或停止该节点服务）；② 观察 CloudNativePG/Strimzi/OpenSearch Operator 是否在预期时间内完成故障转移
- **验收标准**：故障转移在设计方案 4.4 描述的时间窗口内完成，无数据丢失
- **人工确认点**：结果需 DBA/INFRA 人工复核后才计入准出门槛
