## 2. 术语澄清（防止混称，源文档已明确的两处）

| 指标 | 定义 | 不得混称为 |
|---|---|---|
| **资产覆盖率** | `asset_total_count / asset_expected_count × 100`（`gov_metrics/schema.sql` 口径声明）——**分子是 OM 里已登记的资产数，分母是源侧应采集的对象数** | 治理完备度 / 质量检测覆盖率 |
| **治理完备度** | `(asset_total_count - missing_owner) / asset_total_count × 100`——"已登记负责人"的占比 | ❌ 不等于资产覆盖率 |

## 3. 逐项口径

### 3.1 资产目录覆盖率（判据 1）

**公式**：`覆盖率 = OM 已登记资产数 ÷ 源侧应采集对象数 × 100%`

**分母（源侧应采集数）的取得**——必须与"OM 的登记粒度"对齐，口径如下：

| 项 | 约定（**待人工确认，见 §6-1**） |
|---|---|
| 纳入范围 | 试点源**约定的 schema / 库清单**（在 S2-2 接入时由人工圈定） |
| 纳入实体类型 | **table** 为主口径；view / storedProcedure 等**单独列出**，不与 table 混算 |
| 排除项 | 系统 schema（`pg_catalog`/`information_schema`/`mysql`/`performance_schema`/`sys`）、临时表、备份表（`*_bak`、`*_tmp` 类需人工确认清单） |
| 分区表 | PG 分区表**是否把子分区计为独立表**须明确并与 OM 登记粒度对齐 |

```sql
-- PostgreSQL 源库：应采集的表数（分母；只读账号即可执行）
SELECT table_schema, count(*) AS expected_tables
  FROM information_schema.tables
 WHERE table_type = 'BASE TABLE'
   AND table_schema NOT IN ('pg_catalog','information_schema')
   AND table_schema IN (<纳入的schema清单>)
 GROUP BY table_schema ORDER BY 1;

-- MySQL 源库：应采集的表数（分母）
SELECT table_schema, count(*) AS expected_tables
  FROM information_schema.tables
 WHERE table_type = 'BASE TABLE'
   AND table_schema NOT IN ('mysql','performance_schema','sys','information_schema')
   AND table_schema IN (<纳入的库清单>)
 GROUP BY table_schema ORDER BY 1;
```

**分子（OM 已登记数）的取得**：`gov_metrics` ETL 已用 OM 搜索 API 的 `total` 计数（按实体类型分别取），无需另写代码。

**落库（2026-09-18 已落地为自动化机制）**：

| 环节 | 落点/工具 | 说明 |
|---|---|---|
| 分母**存放** | **新参考表 `gov_metrics.asset_expected`**（`source_ref` / `entity_type` / `scope_note` / `expected_count`） | 为什么单独建表：`asset_coverage_snapshot` 每小时由 ETL **重写**，原来的 `asset_expected_count` 恒为 NULL；分母必须放在"只由盘点更新"的参考表里，否则会被 ETL 覆盖回 NULL |
| 分母**取数** | `gov-metrics-etl/coverage_denominator.py`（**默认 dry-run**；`--mode apply` 才落库） | 无 Python 驱动依赖：计数 SQL 交给客户端容器（PG `postgres:16-alpine` / MySQL `mysql:8`）；`--with-om` 会与 OM 已登记对象比对并输出**缺失清单** |
| 分母**消费** | 现有 ETL（`gov_metrics_etl.py`）：每轮读参考表 → 写 `asset_expected_count` 与 `asset_coverage_pct` | **未盘点与覆盖率 0 可区分**：参考表无记录 ⇒ 两个字段写 NULL；有记录 ⇒ 正常计算 |

```bash
# 盘点（dry-run，先看结果）——内网目标记得加 --client-network data-net
python3 /data/ai-governance/scripts/coverage_denominator.py --engine pg \
  --host <源库> --port 5432 --db <库> --user <只读账号> --password-env SRC_RO_PASSWORD \
  --include <schema清单> --source-ref <source-db-1> --scope-note "<纳入范围说明>" \
  --with-om --mode dry-run
# 确认后落库（分母进参考表，ETL 下一轮即算覆盖率）
... --mode apply
```

**已实测（演练，无副作用）**：以 POC 自身 `openmetadata_db.public` 当"源库"→ 分母 **195**、OM 已登记 **0**、缺失 schema 1 ⇒ 覆盖率 **0.00%**；清掉演练行后 ETL 恢复写 NULL。`superset_ro` 可读参考表、**不可写**（`permission denied`）。

> **⚠ 口径留痕要求**：`--scope-note` 必须写清纳入范围（库/schema 清单与排除项）——它是 §6-1 那条"待人工确认口径"的落地证据；改范围 = 改分母，**须留痕**。

**判定规则（关键）**：

1. `覆盖率 = 100%` 的含义是**"缺失清单为空"**，**不是**四舍五入到 100；
2. 因此必须**同时产出缺失清单**（源侧有、OM 没有的对象，逐条列出），供 DE/GOV 复核归因（未授权访问 / 采集范围外 / 采集失败）；
3. 若缺失项属"约定范围外"，须**书面调整范围口径**而不是直接算通过（改口径要人工确认并留痕）。

### 3.2 PII 抽检准确率（判据 2）

**问题**：源文档只写"准确率 >90%"，**未指明是查准还是查全** ⇒ 本文件给两种口径，**建议两者都报、门槛取"查准率"**（**待人工确认，见 §6-2**）：

| 口径 | 公式 | 含义 |
|---|---|---|
| **查准率（precision，建议作门槛）** | 识别为 PII 且人工确认为真 = 对 / **识别为 PII 的总列数** | "报出来的有多少是对的"——治理动作（打标签/脱敏建议）建立在识别结果上，查准率低会**误伤业务** |
| 查全率（recall，建议随附报告） | 人工确认为 PII 且被识别 = 对 / **人工确认为 PII 的总列数** | "真 PII 里漏了多少"——漏检影响合规完整性 |

**抽样方法（建议，样本量待人工确认，见 §6-3）**：

1. **分层**：按 `PII 类型 × 置信度档位`分层（档次见《…S2-5Presidio部署与规则.md》：高/中/低三档）；
2. **每层抽 ≥20 列**（该层不足则全量）；总量建议 ≥100 列；
3. **覆盖到低置信层**——只抽高置信层会得出虚高结论；
4. 抽样列**由 Agent 随机抽取并固定清单**，人工按清单逐列判读（避免"挑好看的"）。

**判读流程**：Agent 给出"源库.表.列 + 识别标签 + 置信度 + 是否被标记" → 人工核对真实语义 → 在 §4.2 表内填"人工判定（对/错/漏）"。

**隐私纪律**（AGENTS §9 / 安全基线⑦）：**抽检记录只留脱敏特征**（例如 `id_card` 识别命中 + 置信度 + 掩码片段 `110***********1234`），**不得**在仓库或记录表里写入真实 PII 原文。

### 3.3 血缘 Top 50 列级准确率（判据 3，ADR-A7）

**Top 50 的遴选**（**待人工确认，见 §6-4**）：建议按"**下游依赖数 + 业务重要性**"排序取前 50 张表，由 DE/GOV 指定并留清单；不得由 Agent 单方决定"哪 50 张算核心"。

**抽检对象**：**列级血缘边**（`上游表.列 → 下游表.列`）。

**抽样方法（建议）**：

1. 从 OM 血缘 API 取 Top 50 表相关的**列级边全集**；
2. 每条边在表中一行；**抽样比例建议 ≥10% 且不少于 50 条**（边数不足则全量）；
3. 人工核对依据：源侧 SQL / 视图定义 / ETL 脚本（**不依赖 OM 自身，避免循环自证**）。

**"正确"的定义（三条同时满足）**：① 该边**真实存在**；② **方向**正确（上游→下游）；③ **列级映射**正确（不是表级蒙对列）。

**判定**：`准确率 = 判定为正确的边数 ÷ 抽检边数 × 100% ≥ 90%`。

**随附材料（ADR-A7 的硬要求）**：`sqllineage` **解析失败的 SQL 清单**（进"待人工确认"队列，**禁止静默丢弃**）——需给出条数、来源对象与处置状态，作为准出材料的一部分呈交。

### 3.4 Superset 全部查询落在 gov_metrics（判据 4）

**正向**：Superset 侧查询日志 / PG 侧 `gov_metrics` 上的查询记录，全部来自 `superset_ro`，且**无一条**落在 OM 内表。
**反向（必须做）**：尝试在 Superset 里访问 OM 内表 → 应失败（已实测 `404 Table not found` + 库级 `permission denied` 兜底）。

> 口径与证据见《…S2-6Superset与指标看板.md》§7/§8；本文件只要求**准出时再复验一次并留输出**。

### 3.5 合规边界文件归档（判据 5）

指门禁④ 的**合规边界确认书**签署归档（SEC + 合规方），见《AI数据治理平台_单机版_S3-1门禁④材料包.md》§4；**续接窗口签约定**（同文件 §5）属 S3-1 门禁④ 的材料，**与 S2 准出并列但不互相替代**。

## 7. 纪律

1. **先定口径、后取数**；口径一旦确定，**变更须留痕**（含变更前后对结论的影响）。
2. **不写真实 PII 原文**（AGENTS §9）；抽检记录只留掩码特征。
3. **判读与签字为人工专属**；Agent 只提供数据、模板与结论指向，**不代判、不代签**。
4. 所有数字须**可回溯**到源文档或实测输出；估算必须标注"工程经验估算，需实测校准"。
