## 0. 设计目标与约束

本次重构的出发点是一张现有门户截图（「所有数据资产」卡片）。原稿的问题不是"丑"，而是**信息无法被解读**：

| 观察到的现象 | 背后的可用性问题 | 本设计系统的对策 |
|---|---|---|
| 大环形图中心只有一个数字 `1`，环本身无刻度无图例 | 图形**不自解释**，读者无法判断 `1` 是总数、占比还是序号 | 环形图强制配**图例 + 中心语义标签 + 分母口径**（见 §4.5） |
| 下方三个数字块 17 / 18 / 19 各带小字 9，彼此无标注 | 三个数字**关系不明**，读者猜不出它们是"分项"还是"趋势" | 数字块升级为带 `label + value + unit + foot` 的 **KPI 卡**，脚注锚定口径 |
| 第 3 个块有蓝色高亮边框，但无文案说明含义 | 用**颜色单一通道**承载状态，色觉障碍用户读不到 | 状态改为**语义色 + 明确文案 + 圆点**三通道（WCAG 1.4.1） |
| 缺少"数据来自哪里／为什么还没有／现在去哪看" | 空状态只给"暂无数据"，用户被困住 | **陈述式空状态**三段式（见 §4.9） |
| 悬浮小字（9）与主数字对比度不足 | 弱化文字大概率低于 4.5:1 | 全量重算对比度，弱化文字定为 `#5f6f7e`（白底 **5.17:1**） |

同时，设计必须服从三条**不可破坏的工程约束**（源自 ADR 与既有实现）：

- **ADR-A6**：门户**只读** `gov_metrics`，不直连 OpenMetadata 内表 → 界面不出现"编辑/写入"类控件
- **ADR-A3**：POC 只做事后审计，不做事前拦截 → 「访问审计」页**不提供**"审批通过"按钮
- **fail-safe**：Agent 未就绪时门户**降级显示**，不报错、不阻塞其他入口 → 未就绪是**正常状态**，不是错误态

## 1. 色彩系统

品牌色选 **深青蓝**（`#0d4d76` 系），替代 Streamlit 默认亮红。理由：治理/审计类后台需要"可信、克制、可长时间注视"的观感，且深蓝能在白底上提供充裕的对比度余量，不必为了达标反复调色。

### 1.0 信息架构（IA 基准，2026-09-20 两轮调整）

页面层级与左侧导航**一一对应**，导航项采用"分级前缀"命名（`首页 / …`、`…（场景 X）`）：

| # | 左侧导航项 | slug | 类型 | 说明 |
|---|---|---|---|---|
| 1 | 首页 / 能力入口 | `home` | 总览 | **统一入口网格**：2 个站内模块 + 5 个外部深链 |
| 2 | 智能问答（场景 D） | `chat` | 站内模块 | 元数据问答（含节点轨迹） |
| 3 | 治理指标 | `metrics` | 站内页面 | 只读 `gov_metrics` 快照 |
| 4 | 访问审计与审批（场景 E） | `audit` | 站内页面 | POC 期仅事后审计（ADR-A3） |
| 5 | 系统状态（运维视角） | `status` | 站内模块 | 下游服务健康度 + 依赖服务清单 |

**第一轮变更缘由**：原设计中「系统状态」与「智能问答」是首页下方的第 2、3 个区块 —— 它们只能通过滚动首页触达，无法被深链引用，也无法在左侧导航中直达。提为独立模块后：

- 两者各获得**稳定的深链地址**（`?page=status` / `?page=chat`），可被运行手册、告警通知、外部文档引用
- 左侧导航从 4 项增至 5 项，导航与页面**完全同构**（不再有"首页里藏着两个功能"的隐式层级）
- 首页回归**纯粹的总览职责**：只负责"去哪"，不承载具体功能

**第二轮变更缘由（系统状态移至末尾）**：`status` 是**运维视角的诊断页**，而 `chat` / `metrics` / `audit` 是业务用户的日常主路径。把运维页插在导航第 2 位，会让业务用户每次扫读导航都要先越过一个与自己无关的页面。移到末尾后：

- 导航遵循「**先业务、后运维**」的阅读顺序，高频路径集中在 1~4 位
- 首页入口网格的站内模块卡**同步调序**（问答在前、系统状态在后）—— 入口卡顺序与导航顺序不一致会制造"两套 IA"的错觉
- `?page=status` 深链语义不变（按 slug 索引，与顺序无关）；侧栏深链提示文案同步为 `?page=home|chat|metrics|audit|status`

**保留的语义**：`系统状态` 与 `智能问答` 在首页入口网格中**依然可见**（带实时状态徽标），因此这两轮变更**没有降低可发现性**，只是把它们从"区块"提升为"一等公民"并重排了位置。

### 1.3 语义色（四类，均"浅底 + 深字"成对）

每类三支：`-bg`（浅底）／`-fg`（深字，用于文字与边框）／`-solid`（饱和色，用于小圆点、进度条等图形元素）。

| 语义 | 浅色 `-bg` | 浅色 `-fg` | 实测 | 深色 `-bg` | 深色 `-fg` | 实测 |
|---|---|---|---|---|---|---|
| success | `#e6f4ed` | `#0a5c3a` | **7.11:1** | `#10352a` | `#6fd4a8` | **7.45:1** |
| warning | `#fdf3e2` | `#7a4a00` | **6.80:1** | `#3a2c12` | `#f0b761` | **7.52:1** |
| danger | `#fdeaea` | `#9b1c25` | **7.01:1** | `#3a1a1e` | `#f0979e` | **7.15:1** |
| info | `#e8f2f9` | `#0f5c8c` | **6.31:1** | `#10304a` | `#85c2e6` | **7.03:1** |
| neutral | `#eef2f5` | `#4a5b6b` | **6.22:1** | `#232f3a` | `#a9b8c6` | **6.73:1** |

**语义映射规则**（不只是"好看"，而是有约定）：

| 语义 | 何时用 | 门户中的实例 |
|---|---|---|
| `info`（蓝） | 中性告知、口径说明、边界声明 | 数据截至时间、POC 边界、`localhost` 隧道提示 |
| `success`（绿） | 服务就绪、操作成功 | "Governance Agent 已就绪" |
| `warning`（橙） | **降级**、能力缺失但系统正常 | "Agent 未就绪 —— 门户已降级" |
| `danger`（红） | **真正的失败**（读库异常、接口报错） | "读取指标层失败：…" |
| `neutral`（灰） | 无状态、不适用 | `—`（NULL）徽标 |

> **关键区分**：Agent 未就绪用 **warning 而非 danger**。因为 fail-safe 降级是**设计内行为**，把它渲染成红色错误会让运维误判系统故障。这条区分写进了 `theme.py` 与 `app.py` 的实现。

### 1.4 深色模式

`tokens.css` 的 `[data-theme="dark"]` 段覆盖 31 个令牌，`theme.py` 的 `_vars_block(dark=True)` 保持同值。**深色不是简单反转**：浅色模式的 success `#0a5c3a`（深绿字）在深底上不可读，深色模式改为 `#6fd4a8`（浅绿字）——即"浅底深字"翻转为"深底浅字"。

## 2. 字体系统

### 2.1 字体栈（中文优先，零 webfont）

```
--font-sans: -apple-system, BlinkMacSystemFont, "Segoe UI",
             "PingFang SC", "Hiragino Sans GB", "Microsoft YaHei",
             "Source Han Sans SC", "Noto Sans CJK SC", sans-serif;

--font-mono: "SF Mono", "JetBrains Mono", Menlo, Consolas,
             "Liberation Mono", monospace;
```

**决策：不使用 webfont。** 中文字体文件动辄 3~8MB，POC 部署在内网、仅回环 `127.0.0.1:8501`，加载体验远不如系统字体。字体栈覆盖 Windows（Microsoft YaHei）、macOS（PingFang SC）、Linux 容器（Noto Sans CJK SC）三平台，**必然命中本地字体**。

### 2.2 类型尺度

| 令牌 | 值 | 用途 |
|---|---|---|
| `--text-xs` | `0.75rem` (12px) | 徽标、脚注、代码块、时间戳 |
| `--text-sm` | `0.8125rem` (13px) | 说明文字、表头、label、note |
| **`--text-base`** | **`0.875rem` (14px)** | **正文基准**、表格单元、按钮 |
| `--text-md` | `1rem` (16px) | 入口卡名称、小标题、KPI 单位 |
| `--text-lg` | `1.125rem` (18px) | 区块标题（h2） |
| `--text-xl` | `1.375rem` (22px) | 页面标题（h1） |
| `--text-2xl` | `1.75rem` (28px) | 小屏 KPI 值 |
| `--text-3xl` | `2.25rem` (36px) | KPI 数值 |

**决策：正文基准取 14px 而非 16px。** 治理后台属**信息密度优先**场景（表格、指标、日志混排），16px 会让首屏信息量骤减。14px 是同类产品（Grafana、Superset、OpenMetadata）的通行基准，配合 1.7 行高保证可读性。

### 2.3 行高与数字对齐

- **中文正文行高 1.7**（西文常用 1.5 在中文方块字下显拥挤）；标题 1.3
- 所有数值（KPI、表格、时间）加 `font-variant-numeric: tabular-nums` —— **等宽数字**保证纵向对齐，扫描一列数字时不会跳动
- **h1/h2 强制收敛**：Streamlit 原生 h1 达 2.75rem，对工具型界面过大，`theme.py` 用 `!important` 压到 22px/18px

### 3.3 阴影（三级 + 焦点环）

| 令牌 | 值 | 用途 |
|---|---|---|
| `--shadow-xs` | `0 1px 2px rgb(16 36 51 / .05)` | 卡片静置态（近乎纸面） |
| `--shadow-sm` | `0 1px 3px … , 0 1px 2px …` | 轻微抬升 |
| `--shadow-md` | `0 4px 12px -2px …` | 卡片悬浮态 |
| `--shadow-focus` | `0 0 0 3px rgb(20 120 180 / .28)` | **键盘焦点环（无障碍必需，禁止移除）** |

阴影统一用 `rgb(R G B / alpha)` 语法（非 `rgba()`），且色相取自品牌深蓝 `#102433` 而非纯黑 —— 纯黑阴影在浅灰底上会发灰脏。

### 3.4 动效

| 令牌 | 值 |
|---|---|
| `--dur-fast` | `120ms`（悬浮、焦点） |
| `--dur-base` | `200ms`（卡片抬升） |
| `--ease-out` | `cubic-bezier(0.16, 1, 0.3, 1)` |

**全局尊重 `prefers-reduced-motion: reduce`**：所有动效降至 `0.01ms`。这是前庭功能障碍用户的硬需求，不是可选优化。

### 3.5 响应式断点

| 断点 | 目标 | 变化 |
|---|---|---|
| ≥1024px | 桌面（主场景，回环访问） | Streamlit `layout="wide"`，入口卡 2 列 |
| 768~1023px | 平板 | 入口卡保持 2 列，KPI 字号降一档 |
| <768px | 窄屏 | KPI 值降至 `--text-2xl`；区块标题降至 `--text-md` |
| <480px | 手机（兜底） | 单列堆叠，触摸目标仍保证 ≥44px |

> 说明：POC 门户通过回环 `127.0.0.1:8501` 访问，**桌面是绝对主场景**。移动端断点存在是为了"能看"，不追求全功能手势优化。

## 4. 组件库

所有组件在 `theme.py::_COMPONENT_CSS` 中实现，**颜色一律 `var(--gv-*)`，零硬编码**。

### 4.1 侧栏导航（radio → 导航列表）

Streamlit 无原生导航组件，用 `st.sidebar.radio` 承载，CSS 改造为导航观感：

- **隐藏原生圆点**（`label > div:first-child { display: none }`），整行成为点击区
- **选中项双通道标识**：`--primary-100` 底色 **+** 左侧 `inset 3px 0 0` 竖条 **+** 文字加粗变色 —— 不依赖单一颜色通道
- 每项 `min-height: 44px`（触摸目标达标）
- 悬浮态：`--primary-50` 底

| 状态 | 底色 | 左竖条 | 文字 |
|---|---|---|---|
| 默认 | 透明 | 无 | `--text-secondary`, 500 |
| 悬浮 | `--primary-50` | 无 | `--text-secondary`, 500 |
| 选中 | `--primary-100` | `3px --primary-600` | `--primary-800`, 600 |
| 键盘焦点 | — | — | `--shadow-focus` 环 |

### 4.2 页面标题区

**h1「🧭 AI 数据治理门户」+ caption 副标题 + 数据截至横幅**。h1 收敛至 22px/600，副标题 13px/次要色。数据截至时间用 `info` 横幅（中性告知，非告警）；若指标层无快照则降级为 `warning`。

### 4.3 区块标题（带序号）

```
[1]  能力入口
     各能力界面由既有平台承载，门户只做统一入口与深链，不重复建设 UI。
```

序号方块 24×24、`--primary-100` 底、`--primary-800` 字；描述 13px 次要色、行高 1.7。
**无障碍**：序号 `aria-hidden`（纯装饰），标题同时通过 `st.subheader` 输出一次，保证屏幕阅读器的标题层级结构不丢 —— 即"视觉装饰"与"语义结构"分离。

### 4.4 能力入口卡片（`a.gv-entry`）

链接型卡片，最小高 76px。结构：`图标 → [名称 + "打开 ↗" 徽标] → 用途描述 → 等宽字体地址 → ›`

| 状态 | 边框 | 阴影 | 位移 |
|---|---|---|---|
| 默认 | `--border` | `--shadow-xs` | — |
| 悬浮 | `--primary-300` | `--shadow-md` | `translateY(-2px)` |
| 焦点 | — | `--shadow-focus` | — |

**设计要点**：地址用等宽字体显示完整 URL，便于运维肉眼核对端口（`8585`/`8088`/`8080`/`9090`/`9093`）。`localhost` 系列额外加一行 caption 说明需开 SSH 隧道。

#### 4.4.1 站内模块卡变体（`a.gv-entry--internal`）

**IA 变更（2026-09-20）后引入。** 首页「能力入口」改为**统一入口网格**：站内模块（系统状态、智能问答）与外部深链同网格并列。两类卡片若长得完全一样，用户点下去才知道是不是离开本站 —— 那是很差的心智模型。故给站内模块一个**同族但可辨**的变体：

| 属性 | 外部深链卡 | 站内模块卡（`--internal`） |
|---|---|---|
| 左侧强调条 | 无 | `inset 3px 0 0 --primary-600` |
| 底色 | `--surface` | `--primary-50 → --surface` 42% 渐变 |
| 边框 | `--border` | `--primary-200` |
| 箭头符号 | `↗`（新窗口） | `›`（站内前进） |
| 链接目标 | `target="_blank" rel="noopener"` | 站内页面链接 |
| 徽标 | 「打开 ↗」 | **实时状态徽标**（可用 / 降级中 / 全部正常） |

**无障碍考量**：箭头符号与左侧竖条构成**形状 + 颜色双通道**区分，不依赖单一颜色通道（WCAG 1.4.1）。站内卡额外承载实时状态徽标 —— 用户不必进入页面就知道 Agent 是否就绪。

**为什么用左侧竖条而不是只换边框色？** 竖条在等高卡片网格中形成一条**纵向节奏线**，扫视时能立刻分组；且不额外占用高度，不破坏 76px 的最小触摸目标。

### 4.5 环形图（`gv-donut` + `gv-legend`）

**这是对原截图最关键的改造。** 原稿是"大环 + 中心单数字 + 下方孤立小方块"，读者无法解读。新设计强制三联：

1. **中心**：大数值 + 其下语义标签（如"已登记资产"）
2. **环体**：单一数据用整环填充度表达，环粗 `stroke-width: 24`（`r=76`，200×200 viewBox），缺口用 `--border` 色
3. **图例**：明确列出 `颜色 → 标签 → 数值 → 占比`，**与环扇区一一对应**

口径不确定时（如 `asset_coverage_pct` 为 NULL），中心显示 **`—`** 而非 `0%`，并在图例下方注明"不适用（NULL ≠ 零）"。

### 4.6 徽标（`.gv-badge`，5 变体）

| 变体 | 底色 | 文字 |
|---|---|---|
| `--ok` | `--success-bg` | `--success-fg` |
| `--warn` | `--warning-bg` | `--warning-fg` |
| `--err` | `--danger-bg` | `--danger-fg` |
| `--info` | `--info-bg` | `--info-fg` |
| `--mute` | `--neutral-bg` | `--neutral-fg` |

结构：`<span class="gv-badge"><span class="gv-badge__dot"></span>文案</span>` —— **圆点（图形）+ 文案（文字）双通道**，色盲用户凭小圆点形状与文案仍可辨读。

### 4.7 横幅（`stAlert` 四色重绘）

覆盖 Streamlit 原生 `st.success/warning/error/info`：`--radius-lg` 圆角、1px 语义色边框、`--space-4/5` 内边距、无阴影。正文 13px/1.7。

### 4.8 KPI 卡（`gv-kpi` / `st.metric`）

```
┌─────────────────────────────┐
│ 已登记资产总数                │  ← label  13px 次要色
│ 1 个                        │  ← value  36px/700 tabular-nums + unit
│ ─────────────────────────── │  ← 分隔线
│ 口径：asset_total_count 求和  │  ← foot  12px 弱化色，锚定口径
└─────────────────────────────┘
```

- `.gv-kpi--accent` 变体：左侧 `3px --primary-600` 竖条，用于首屏主指标
- **脚注 `foot` 是核心设计**：原截图"17/18/19"最大的问题是口径不明。脚注强制承载"这个数字怎么算的"，避免数字随口径漂移而无人察觉
- 无数据时 value 显示 **`—`** 并在脚注写明"无法计算（`—` 表示不适用，不等于 0）"

### 4.9 空状态（`.gv-empty`）

**三段式文案**，替换裸"暂无数据"：

1. **标题** —— 说明缺什么（"暂无质量数据"）
2. **来源** —— 数据从哪来（"质量趋势在接入业务源并跑通质量测试后产生"）
3. **出路** —— 现在去哪看（"当前 POC 仅接入平台自身指标，尚无业务源质量样本"）

即使没有数据，用户也知道**下一步该做什么**。

### 4.10 表格（`st.dataframe`）

`--radius-lg` 圆角容器 + `--border` 边框 + `--shadow-xs`；表头 `--surface-sunken` 底、13px/600/次要色；单元 14px/`tabular-nums`。

### 4.11 按钮（三种）

| 类型 | 底色 | 文字 | 边框 |
|---|---|---|---|
| primary | `--primary-700` | `--text-inverse` | 同底色 |
| primary hover | `--primary-800` | — | 同底色 |
| secondary | `--surface` | `--primary-700` | `--border-strong` |
| secondary hover | `--primary-50` | — | `--primary-600` |

全部 `min-height: 44px`、`--radius-md`、600 字重、`focus-visible` 显示焦点环。

### 4.12 输入框（`stTextInput`）

`min-height: 44px`、`--border-strong` 边界（4.30:1 ≥3:1）、聚焦时边框转 `--primary-600` + 焦点环、placeholder 用 `--text-muted`（5.17:1）。label 13px/500/主色。

### 4.13 口径提示条（`.gv-note`）

左 `3px --primary-600` 竖条 + `--primary-50` 底 + 右侧圆角。**与横幅语义区分**：note 是"口径说明/边界声明"（中性、常驻），横幅是"状态告知"（临时、事件性）。用视觉形式区分二者，避免读者把口径说明当告警。

### 4.14 折叠区（`st.expander`）

用于"探测详情（GA `/health` 原始返回）"等技术细节。`summary` 高 44px，默认收起 —— **主流程展示人话，原始数据按需展开**。

### 4.15 问答组件（`.gv-chat-user` + `.gv-trace`）

用户提问气泡：`--primary-50` 底 + `--primary-200` 边框 + `--radius-lg`。
**节点轨迹**（`.gv-trace`）：等宽字体、`--surface-sunken` 底、展示 LangGraph 节点名与上下文预算口径。

### 5.5 其他

- **`prefers-reduced-motion`**：全局动效降至 0.01ms
- **文字缩放**：全站 `rem` 单位，浏览器缩放到 200% 布局不破
- **语义 HTML**：标题用 `h1`/`h2` 层级、表格用 `role="columnheader"/"gridcell"`、装饰元素 `aria-hidden="true"`
- **HTML 转义**：所有拼入 markdown 的外部文本经 `html.escape()`，防注入与渲染错乱
- **`.sr-only` 工具类**：视觉隐藏但**保留在无障碍树**中（`clip-path: inset(50%)` 而非 `display:none`）。用于给无可见标题的容器（如表格）补充可访问名称。**注意与 `hidden` 的区别** —— 后者会把元素一并从无障碍树移除，屏幕阅读器也读不到。

> ⚠️ **一处曾被漏掉的无障碍缺陷**：mockup 的依赖服务清单表格用了 `<caption class="sr-only">`，但 `.sr-only` **从未在任何 CSS 中定义** —— 结果这个"仅供屏幕阅读器"的 caption 被**可见渲染**，与视觉标题重复。
> 这类缺陷的特点是：**浏览器不报错、正则看不出、目视容易忽略**。已补上 `.sr-only` 定义，并在 `check_mockup_nav.py` 新增 N9 组（类名完整性）防止此类"引用了但没定义"的问题再次溜过。

## 6. Streamlit 落地映射

设计系统通过**两条渠道**落地 Streamlit，分工明确：

### 6.1 渠道 A：`.streamlit/config.toml` 的 `[theme]` 段（结构化，优先级最高）

由 `theme.py::emit_config_toml()` 生成：

```toml
[theme]
primaryColor = "#0d4d76"
backgroundColor = "#ffffff"
secondaryBackgroundColor = "#f7f9fb"
textColor = "#1a2733"
font = "sans serif"
```

**覆盖范围**：主按钮/强调色、主区底、侧栏与凹陷底、正文色、基础字体族。这是 Streamlit **官方支持**的换肤入口，稳定、不受内部 DOM 变更影响。

### 6.2 渠道 B：注入式 `<style>`（`theme.inject_css(st)`）

用于 config.toml 覆盖不到的部分。分两块：

1. **`--gv-*` 令牌声明块**（`_vars_block()`）—— 与 `tokens.css` 同值
2. **组件样式**（`_COMPONENT_CSS`）—— 消费令牌，覆盖原生控件 + 提供自绘组件类

**覆盖范围**：h1/h2 尺度收敛、侧栏 radio 导航化、按钮/输入框/横幅/表格/折叠区重绘、`.gv-*` 自绘组件（卡片、徽标、KPI、空状态、note、入口卡、问答气泡）。

### 6.2.1 mockup 组件 → Streamlit 落地方式对照（**交付必读**）

`mockup.html` 与 `theme.py` 的组件类**并非一一对应**，这是**有意为之**：mockup 需要用自绘 HTML 模拟整个应用外壳（它没有 Streamlit 运行时），而落地层应当**优先复用 Streamlit 原生控件**（可聚焦、可测、随版本升级）。下表逐类说明归属，消除"设计稿有、落地层没有"的模糊地带。

**A 类 —— 直接对应（`theme.py` 提供同名类，`app.py` 直接用）**

| mockup 类 | 落地层 | 说明 |
|---|---|---|
| `.gv-card` | `theme.py` 同名 | 卡片容器 |
| `.gv-badge` / `--ok/--warn/--err/--info/--mute` | 同名 | 徽标 5 变体 |
| `.gv-kpi` / `--accent` / `__label` / `__value` / `__unit` / `__foot` | 同名 | KPI 卡（`app.py::_kpi()` 拼 HTML） |
| `.gv-entry` / `--internal` / `__name` / `__desc` / `__hint` | 同名 | 入口卡（`app.py::_entry_card()`） |
| `.gv-note` | 同名 | 口径提示条（`app.py::_note()`） |
| `.gv-empty` / `__title` / `__text` | 同名 | 空状态（`app.py::_empty()`） |
| `.gv-section-title` / `.gv-section-num` / `.gv-section-desc` | 同名 | 区块标题（`app.py::_section()`） |
| `.gv-trace` | 同名 | 节点轨迹标签 |
| `.gv-mono` | 同名 | 等宽标识符 |

**B 类 —— 用 Streamlit 原生控件替代（mockup 的自绘类**不**进落地层）**

| mockup 类 | 落地方式 | 为什么不用自绘 |
|---|---|---|
| `.gv-banner`（4 色横幅） | `st.success/warning/error/info` + `theme.py` 的 `[data-testid="stAlert"]` 重绘 | 原生 alert 自带 `role="status"` / `role="alert"`，无障碍语义现成；自绘会丢 |
| `.gv-disclosure` | `st.expander` | 原生 `<details>` 等价的键盘与 ARIA 行为已实现，不必重造 |
| `.gv-code` | `st.code` / `<code>` | 原生代码块 + 全局 `code,pre` 样式 |
| `.gv-table` / `.gv-table-wrap` | `st.dataframe` | 见 §6.4：canvas 渲染，只能做**容器级**样式（圆角/边框/表头底） |
| `.gv-btn` / `--primary/--secondary/--ghost/--sm` | `.stButton > button[kind=…]` | 原生按钮 focus / disabled 行为不可替代 |
| `.gv-input` / `.gv-field` / `.gv-label` / `.gv-help` | `st.text_input` / `st.text_area` + `[data-testid="stWidgetLabel"]` | 原生输入控件 |
| `.gv-nav` / `__list` / `__item` / `__link` / `__icon` / `__brand` / `__foot` | `st.sidebar.radio` + `theme.py` 的 radio 导航化样式 | 见 §4.1；原生 radio 可被 `AppTest` 断言，自绘不可 |
| `.gv-asof`（数据截至 chip） | `st.info(...)` | 复用现成语义色横幅，不额外造 chip |
| `.gv-msg` / `.gv-chat-log` / `.gv-chat-user` | `st.chat_message` / `st.markdown` + `.gv-chat-user` | 只保留**用户气泡**一个自绘类；AI 侧走原生 |

**C 类 —— 仅设计稿存在，落地层**不需要**（壳层 / 评审辅助）**

| mockup 类 | 为什么落地层没有 |
|---|---|
| `.gv-app` / `.gv-main` / `.gv-content` / `.gv-topbar` | 这些是**应用外壳**。Streamlit 自带 `stApp` / 侧栏 / 主区布局，自造外壳等于与框架对抗 |
| `.gv-chart` / `.gv-donut` / `.gv-legend` | 环形图在落地层由 `st.metric` 组合或后续接入图表库；纯 CSS 环形图仅用于设计稿演示 |
| `.gv-skip` | Streamlit 主区无"跳过多级导航"需求（侧栏为单层 radio）；若未来加多层导航需补回 |
| `.gv-grid-2` / `.gv-stack` | 布局由 `st.columns()` 承担 |
| `.gv-num` | `st.dataframe` 的数值列对齐由列配置控制 |
| `.ds-*`（`ds-shell` / `ds-head` / `ds-theme-btn` / `ds-panel`） | **设计稿外壳**：承载说明文字与主题切换，非产品功能 |

> **交付纪律**：改 `mockup.html` 的组件时，按下表判断它属于 A/B/C 哪一类 ——
> A 类须同步 `theme.py`；B/C 类**不得**为了"与设计稿一致"而在落地层重复造轮子。
> `tools/check_mockup_nav.py` 的 N9 组保证 mockup 自身类名无悬空引用。

### 6.3 双令牌前缀（有意设计）

| 侧 | 前缀 | 示例 |
|---|---|---|
| `design/tokens.css` | `--color-*` | `--color-primary-600` |
| `theme.py::TOKENS` | `--gv-*` | `--gv-primary-600` |

**为什么不用同一套前缀？** Streamlit 自身与 BaseWeb 已占用大量 CSS 变量。若沿用 `--color-*`，注入的变量可能与 Streamlit 内部变量**同名覆盖**，造成难排查的样式污染。`--gv-` 前缀（governance）保证命名空间隔离。

代价是"两侧比对需要映射"。`check_tokens.py` 内置**显式映射表** `_name_map`（长前缀优先匹配，如 `--color-surface-sunken` 先于 `--color-surface`）完成 64 项逐项校验 —— 前缀差异**不产生校验盲区**。

### 6.4 受 Streamlit 限制的部分（明确告知开发）

| 限制 | 影响 | 当前处置 |
|---|---|---|
| `st.dataframe` 由 **canvas 渲染**，单元格文本不在 DOM 中 | 无法对表格单元做 CSS 精细控制、无法读取 innerText 做断言 | 只做容器级样式（圆角/边框/表头底）；需要精细排版时改用 `st.table` 或自绘 HTML |
| 内部 DOM 结构与 `data-testid` 随版本变动 | 选择器可能在小版本升级后失效 | 依赖 `data-testid`，并**锁定 streamlit 1.64.0**；升级时须重跑视觉核对 |
| CSS 注入**无法改深层 shadow DOM** | 部分 BaseWeb 内部元素样式无法触及 | 用 `[data-baseweb="…"]` 属性选择器在可及层覆盖 |
| 无客户端动画 API | 微动效依赖 CSS transition | 已限制在悬浮/焦点等轻量场景 |

### 6.5 变更纪律

1. 改任何颜色 → **必须**重跑 `python tools/check_tokens.py`（令牌一致性 64 项 + 深色覆盖 31 项 + 对比度 28 组）
2. 改令牌 → `tokens.css` 与 `theme.py::TOKENS` **两处同步**，否则校验脚本报 DIFF
3. `app.py` **不写死任何色值**（当前为 0 处硬编码）
4. 视觉变更须保持既有自动化断言文案不变（见 §7.2）

### 7.3.1 一次真实的回归：mockup 侧栏出现重复项

**现象**：2026-09-20，用户截图反馈 mockup 侧栏底部多出一项独立框起的「访问审计与审批（场景 E）」，与导航列表中的同名项重复。

**根因（HTML 结构非法，非 CSS 问题）**：`panel-home` 的 `<ul class="gv-nav__list">` 在最后一个 `<li>` 之后**提前闭合**，紧随其后的又一个 `<li>` 成了 `<ul>` 之外的**孤儿元素**（并伴随一个多余的 `</ul>`）。浏览器 HTML 解析器会忽略多余的 `</ul>`，并把孤儿 `<li>` 提升到 `<nav>` 下渲染 —— 于是它在导航列表视觉之外独立成行。

**同批修掉的连带缺陷**：`panel-metrics` / `panel-chat` / `panel-audit` 三份 nav 各只有 4 项（缺「访问审计与审批」），且**全部链接是 `href="#"` 死链**，顺序也与 IA 基准不符。根因是这 4 份 nav 在手工复制时没有同步更新。

**修复与防线**：
1. 5 份 nav 统一为**同构**：5 项、正确的 `#panel-*` 锚点、各自的 `aria-current="page"`、顺序符合 IA 基准
2. 新增 `tools/check_mockup_nav.py`（39 项）：校验 `<ul>` 配对、**孤儿 `<li>` 检测**、项数、死链、顺序、`aria-current`、5 份 nav 同构
3. 回归脚本新增 group [8]，直接内联同一批结构断言 —— 这类"复制 nav 时漏改"的缺陷现在会被 CI 拦住

**设计层面的教训**：mockup 里每个 panel 复制一份完整 nav，是**为可独立预览而做的取舍**（每页都不依赖 JS 切页就能看清侧栏状态）。代价是 5 份 nav 需手工保持同构 —— 因此必须有结构校验兜底。详见 §7.3.2。

### 7.3.2 为什么不把 mockup 的侧栏抽成一个共享组件

mockup 是**静态 HTML 高保真稿**，没有构建步骤，`<template>` / `fetch()` 注入都会引入本地文件协议下的限制（`file://` 下 `fetch` 被 CORS 拦截）。权衡后保留"每个 panel 自带一份 nav"：

- **收益**：每个 panel 都可被单独截图/单独审阅，侧栏的选中态（`aria-current`）与内容页正确对应
- **代价**：5 份 nav 需手工同构
- **兜底**：`tools/check_mockup_nav.py` 把"同构"变成可执行断言 —— **用校验替代抽象**，对静态稿是更划算的选择

如果未来 mockup 迁到带构建步骤的环境（Vite/Astro 等），应优先抽成共享组件。

### 7.3.3 一次静态稿校对：`.sr-only` 从未定义 + 评审批注残留

**背景**：`mockup.html` 经历多轮 IA 调整与 tabbar 删除后，需要一次系统性校对（而非再改功能）。

**查出的两类问题**：

| # | 问题 | 性质 | 为什么之前的校验没抓到 |
|---|---|---|---|
| 1 | `<caption class="sr-only">` 引用了**从未定义**的 `.sr-only` | **无障碍缺陷**（反向）：本应仅屏幕阅读器可见的表格标题被**可见渲染**，与视觉标题重复 | 正则查不出"用了但没定义"；浏览器不报错；目视易忽略 |
| 2 | 设计稿正文含"原稿的问题是…"「图形替代原『大环 + 三个孤立数字块』」等文字 | **交付缺陷**：设计稿是**产品视觉基准**，这类写给评审者的话会随稿子被当成产品文案 | 文字本身合法，只有对照上下文才能判断口吻不对 |
| 3 | `panel-status` 的 nav footer 结构与其余 4 份**不一致**（用 `<p>` 包裹而非纯文本） | 一致性问题：5 份 nav 本应同构 | 只校验了导航项，没校验 footer |
| 4 | `panel-metrics` / `panel-audit` 的区块标题缺序号，与 `panel-home` 的"1"不统一 | 一致性问题 | 序号是装饰，无校验 |
| 5 | 文档 §4.5 称"环粗 `14px`"，实际为 `stroke-width="24"` | **文档漂移** | 数字写在散文里，无交叉校验 |

**处置**：
1. 补 `.sr-only` 定义（`clip-path: inset(50%)` 而非 `display:none` —— 后者会一并移出无障碍树）
2. 设计稿正文改为产品口吻；设计意图说明移入 HTML 注释与本文档
3. 5 份 nav footer 统一为同构结构
4. 区块标题统一带序号
5. 修正文档中的环形图描边值

**新增防线（`check_mockup_nav.py` 由 39 增至 42 项）**：

| 断言 | 作用 |
|---|---|
| `N9a` mockup 引用的 CSS 类均有定义 | 捕捉"用了但没定义"（本次 `.sr-only` 这类缺陷） |
| `N9b` `.sr-only` 工具类已定义 | 单点兜底：无障碍工具类必须存在 |
| `N10` 正文无评审批注口吻残留 | 关键词黑名单（`原稿` / `原截图` / `替代原` / `读者无法` …），扫描**剔除注释后的正文** |

> **方法论**：这三条断言都不是"功能正确性"检查，而是**产出物一致性**检查。它们捕捉的是"东西能跑但不像成品"的问题 —— 恰恰是人工评审最容易漏、又最影响交付专业度的一类。关键词黑名单需随文案演进维护（`N10` 的 `reviewer_voice` 列表）。
