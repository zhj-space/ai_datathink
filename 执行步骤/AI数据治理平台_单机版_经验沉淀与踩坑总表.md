## 0. 一页结论（六条主线）

| # | 主线 | 一句话（都是踩出来的） |
|---|---|---|
| 1 | **不报错 ≠ 生效** | 本 POC 最贵的坑全是"静默失效"：规则编译通过却不触发、指标抓取 `up` 却没数据、权限改了但池连接还在、`planned` 其实没写进 OM。**新东西必须做一次真实触发验证**（§3） |
| 2 | **浮动的东西会在重建时被动"换血"** | 浮动基础镜像 `python:3.12-slim` 静默把 debian 13.6 换成 13.7（HIGH/CRIT 由 10/3 变 0/0），且**没有任何报错** ⇒ 基础钉 digest、依赖钉版本（§2A） |
| 3 | **判据选错会得出反向结论** | 空库归档 TOC=0 被判"恢复失败"、`increase()` 漏报"首次采集前就 OOM"、`refresh=false` 下 `_count=0`、被拒的 bulk 依然"很快"（§4） |
| 4 | **口径先于数字** | 容器数 18/19、规则数逐轮演进（12→21→22→27→34→40）——同一事实的不同口径必须有唯一定义，引用时必须指明口径（§4） |
| 5 | **边界要写在纸上** | 每个"已完成"都要配一份"未证明 / 不做"清单：自压基线 ≠ 准出判据、dump 恢复 ≠ PITR、抓取 `up` ≠ 有数据（§5） |
| 6 | **凭证与主机名一旦推送就收不回** | 脱敏必须在首次 push **之前**做完；事后重写历史 + force-push 之后，远端**旧对象仍可按 SHA 拉取**（实测）⇒ 只能改 private / 删库重建（§6） |

## 2. 分主题经验（下次直接照做）

### A. 镜像与供应链

| 现象（实测） | 定式做法 | 出处 |
|---|---|---|
| 浮动 tag `FROM python:3.12-slim` 在重建时**静默换基础**（debian 13.6→13.7），HIGH/CRIT 从 10/3 变 0/0 | 自建镜像的 `FROM` **必须固定 digest**；换基础属组件版本变更，须记录并重跑验收 + 重扫 | `AGENTS.md` §7、`执行步骤/AI数据治理平台_单机版_供应链漏洞处置清单.md` |
| 误把**旧的** `78387bc3881b…` 当成"新 digest"钉上去，重扫又回到 13，**且无任何报错** | 钉完 digest **必须重扫验证**；本地 tag 与"新 digest"要**分别核实**，必要时先 `docker pull` 再取 digest | `AGENTS.md` §7、`执行步骤/单机版部署计划.md` v4.10 记录 |
| `flink-connector-kafka` 是**瘦包**：只装 CDC + Kafka 连接器 ⇒ 冒烟作业立即 `ClassNotFoundException: …OffsetResetStrategy` | 一并补 `flink-connector-base` **与 `kafka-clients`**（后者官方基础镜像也不含）；连接器 JAR 按 `jars.sha256` 构建期强校验 | `执行步骤/AI数据治理平台_单机版_S3前置部署记录.md` §4、`flink-image/README.md` |
| Superset 官方 lean 镜像**无 PG 驱动**；官方镜像 venv 无 `pip` | 驱动装进镜像自带 venv（`/app/.venv`），用镜像自带 `uv` 装；**依赖必须钉版本**（`psycopg2-binary==2.9.13`） | `superset-image/README.md` |
| `docker compose build superset` 是 **no-op**（该镜像是手工 `docker build`，compose 无 `build` 段） | 改镜像按实际构建路径操作；改 compose 的 `image:` 行须走"**去 digest → build → 取新 image ID → 重新钉 digest**" | `superset-image/README.md`、`AGENTS.md` §7 |
| **重建不降漏洞**（实测 100 → 100） | 要降必须升版本或显式升级个别依赖，**且需人工批准**；不得声称"重建即修复" | `superset-image/README.md`、`AGENTS.md` §7 |
| `trivy image` 默认先更新漏洞库，常达数分钟甚至超出会话窗口 | 本地库为当日时用 `--skip-db-update`（实测 2 秒出结果）；**别用 `nohup … &` 后台跑**（会随会话被带走） | `AGENTS.md` §7 |

### B. 数据库与连接池（PgBouncer 是硬约束 2）

| 现象（实测） | 定式做法 | 出处 |
|---|---|---|
| 权限收紧后 `superset_ro` **经 PgBouncer 仍能连**目标库（直连 PG 已被正确拒绝） | **任何库级/角色级权限变更，必须回收 PgBouncer 池连接后才算生效**（`RECONNECT`），改完必须复验 | `执行步骤/AI数据治理平台_单机版_S2-5gov_metrics与ETL.md` §5 |
| 经 PgBouncer 建库后 `DROP DATABASE` 被池内连接挡住，留下残留库 | 删库前先回收池连接，再删、再**验证零残留** | `capacity-baseline/README.md`、`AGENTS.md` §7 |
| 新建库默认带 **PUBLIC CONNECT** ⇒ 未收敛就等于人人可连 | 新建库**必须做库级 CONNECT 收敛**（`REVOKE … FROM PUBLIC` + 按需 GRANT），并做反向验证（该拒的必须被拒） | `AGENTS.md` §7、`governance-agent/README.md` |
| 重启 PgBouncer 后 Airflow 组件短暂 `starting` | `restart: unless-stopped` 兜住、约 1 分钟自愈——**属预期行为**，不要据此中止流程 | `执行步骤/AI数据治理平台_单机版_S2-5gov_metrics与ETL.md` §5 |
| `docker exec psql` 写库报 `SASL authentication failed` | 显式传 `-e PGPASSWORD=<取自服务器 .env>`；**口令不入仓库** | 同上 §5 |

### C. 监控与告警（Prometheus 系）

| 现象（实测） | 定式做法 | 出处 |
|---|---|---|
| 自定义指标标签用了 **`job`**，被 Prometheus 改名 `exported_job` ⇒ 规则**静默失效** | 自定义标签统一用 `task` / `container`+`name`；保留 `count<预期`、`absent()` 护栏 | `AGENTS.md` §7、`alerting/README.md` |
| 跨源组合 `A and B` 因**标签集不同永不匹配**，规则永远 `inactive`（条件满足也不报） | 跨源必须写 **`and on()`**；**新规则必须做一次真实触发验证**（造条件 → 看 `pending → firing` → 还原），不能只看 `promtool check rules` 通过 | `AGENTS.md` §7、`alerting/README.md` |
| 指标类采集器**任何一行非数字会让 node_exporter 拒收整个 textfile 文件**（一行空值 ⇒ 所有新鲜度指标一起消失） | 取值 `num_or0()` 兜底 + **原子写入 + 逐行格式自检**（非法则保留旧文件）；新增指标带 `# HELP`/`# TYPE` 并过 `promtool check metrics` | `AGENTS.md` §7 |
| 容器级指标"抓取目标 `up` ≠ 有数据"（cAdvisor 在本环境只导出根 cgroup） | 判"有没有数"要看**序列本身**；容器级指标以自采 `container_probe.sh` 为准 | `AGENTS.md` §7、`alerting/README.md` v1.2 |
| 同一 series 有两个生产者 ⇒ 抓取直接失败 | **每个采集器写独立 textfile 文件、独立 cron**；同一 series 只能有一个生产者（Ollama 探针已同步移除容器指标） | `alerting/README.md` v1.2 |
| 文件系统类规则不加过滤会命中 `/boot/efi`（约 200 MB ESP）造成假阳性 | 文本类/磁盘类规则**必须限定 `mountpoint`**（只盯 `/` 与 `/data`） | `alerting/README.md` §1b |
| 告警"有判定、无留痕"：21 条规则在跑，Alertmanager 原 receiver 为空 | 告警必须**汇入 GA 落库**（`POST /api/v1/alerts/ingest` + Bearer 强制校验 + 幂等键 `alertmanager:<fingerprint>:<status>`）；**留痕 ≠ 通知到人**，IM 地址到位前不得声称"能通知" | `执行步骤/AI数据治理平台_单机版_S3-6治理Agent首版实现记录.md` v1.1 |
| AM 未启用 lifecycle API，`/-/reload` 不可用 | 配置生效走 `SIGHUP` 热加载；流程固定为 `amtool check-config` → `SIGHUP` → 核对状态 | `AGENTS.md` §7 |

### D. 血缘与 OpenMetadata API

| 现象（实测） | 定式做法 | 出处 |
|---|---|---|
| 按 OM 血缘响应顶层 `toEntity` 判"边是否存在"会**永远 False** ⇒ 对账误报漂移并反复"假修复" | 用 `GET /lineage/getLineageEdge/…` 并读 **`edge` 键**（存在时返回 `{"edge":{…}}`） | `AGENTS.md` §7、`执行步骤/AI数据治理平台_单机版_S3-6治理Agent接口规格.md` v1.4 |
| 状态 `planned` 被当成"已在 OM"（"行存在即跳过"）⇒ 主路径**永远写不进** OM | 只有 `status='applied'` 才算已写入；`planned`/`drift`/`entity_missing`/`failed` **必须重推** | `AGENTS.md` §7 |
| OM 删实体**连带删边**，而 GA 状态仍 `applied` ⇒ 已知漂移 | 必须有**周期对账**（cron 04:10 + `LineageReconcileStale` >30h）；**对账只新增/修复，绝不删除 OM 上的任何边**（他源血缘不归本服务管） | `AGENTS.md` §7 |
| 清理顺序写反，留下残留实体 | 清理按依赖倒序，并把**"临时对象零残留（须打印 `(none)`）"作为自检项** | `执行步骤/AI数据治理平台_单机版_S3-5血缘上报D1记录.md` §5 |
| Flink SQL 字符串用双引号 / 含括号被误判（如窗口 TVF） | Flink SQL **字符串必须单引号**；改"SQL 文件 + `docker cp`"避免 shell 引号；解析不确定时**拒绝上报**（400 + errors、不落任何行），**宁缺勿错** | `执行步骤/AI数据治理平台_单机版_S3前置部署记录.md` §12、`AGENTS.md` §7 |

### E. RAG 与本地 AI

| 现象（实测） | 定式做法 | 出处 |
|---|---|---|
| **Ollama 默认 `num_ctx` 仅 2050**，超长 prompt 被**静默截断**（不报错） | 必须**显式**设 `GA_RAG_NUM_CTX`（默认 4096）+ 上下文预算 `GA_RAG_CTX_BUDGET_TOKENS`（默认 1800，口径 = **整条 prompt**）；"设了预算"不等于"没超" | `AGENTS.md` §7、`README.md` §1 |
| 回答可能编造资产标识 | **引用必须程序化校验**：不存在的标识标注"未核实"；验收含**防幻觉负例**与引用校验真假两态 | `执行步骤/AI数据治理平台_单机版_S4-2RAG最小闭环记录.md`、`…测试入口与用例.md` |
| 改代码后容器行为没变 | **新增模块必须同步 Dockerfile 的 `COPY`**（漏 COPY 是高频坑）；补丁脚本必须**幂等**（非幂等曾导致 compose 出现重复 key）；`docker cp` 后注意属主 | `执行步骤/AI数据治理平台_单机版_S4-2RAG最小闭环记录.md` §4 |
| 手工跑脚本报找不到模块 | 该镜像 `presidio_analyzer` 是 `/app` 下源码目录 ⇒ 自定义脚本须 `PYTHONPATH=/app` | `执行步骤/AI数据治理平台_部署步骤_单机版.md` S2-5 |
| 接口调用字段漏传却"没报错" | 漏传字段会**静默落入"低风险/无告警"** ⇒ 调用方必须**显式断言字段齐全**（PII 判据 `data.governance.config.pii_tags`、角色字段 `user_roles`、时段 `hour_utc`） | `执行步骤/AI数据治理平台_单机版_S2-5OPA策略与部署.md` |

### F. 指标与数据口径

| 现象（实测） | 定式做法 | 出处 |
|---|---|---|
| 覆盖率分母硬编码 NULL，手工 UPDATE 会被下一轮 ETL 重写回 NULL | 分母放**独立参考表**（只由盘点工具更新），**不得写进每小时重写的快照表**；盘点范围用 `--scope-note` 留痕 | `执行步骤/AI数据治理平台_单机版_S2-5gov_metrics与ETL.md` §7 |
| 快照基线与增量窗口混用 | **快照基线 = 权威质量指标（进看板）；增量窗口 = 异常告警（不进质量看板）**（ADR-A5） | `AGENTS.md` §4 |
| `rate(metric[7d])` 得出"7 天水位 68.5%" | 窗口外推会失真 ⇒ 用 `avg_over_time(rate(metric[5m])[d:5m])`；**只报实测净变化，不做事先外推** | `执行步骤/AI数据治理平台_单机版_S4-4水位周报机制记录.md` §5 |
| 只有 2.2 天数据却标"7/14 天均值：未触发" | 先实测数据跨度（`SPAN`），跨度不足写**"数据不足"**，不写"未触发" | 同上 §5 |
| 取数失败**不报错**，只是静默变成 `N/A` | 关键项**保留 `N/A` 字样不吞掉**，便于人工发现；多层引号下 `curl \| python3 -c` 转义易失败 ⇒ 统一改走 `urllib` 取数 | 同上 §5 |

### H. 备份与恢复

| 现象（实测） | 定式做法 | 出处 |
|---|---|---|
| 用"行首数字计数"判归档有效性，把**空库归档判成失败** | 判据用 `pg_restore -l` 可解析 **且 TOC Entries > 0**（空库归档只有注释级条目） | `执行步骤/AI数据治理平台_单机版_S1部署记录.md`（校验判据） |
| 把 dump 恢复说成 PITR | **PG PITR 在本环境不存在**（未启用 WAL 归档）⇒ 不得把 dump 恢复说成 PITR；对象级恢复耗时 ≠ 主机级 RTO | `AGENTS.md` §7、`restore-annual-drill/README.md` |
| 配置归档含**真实密钥**，落盘解包后遗留 | 解包目录必须在 `/tmp`、**用毕即删**、删除前**断言路径前缀**；恢复必须一并恢复密钥，否则 JWT/加密数据不可用 | `AGENTS.md` §7 |
| 数值比较用字符串比较（`12.5 < 1.5` 判反） | 数值比较用 `awk`，不用 shell 字符串比较 | `AGENTS.md` §7 |
| 恢复演练结论被放大 | 报告固定声明**未覆盖项** ⇒ **不得声称"全灾备可用"**；演练判读属人工 | `restore-annual-drill/README.md` |

### I. Windows 侧与远程执行

| 现象（实测） | 定式做法 | 出处 |

## 3. 静默失效清单（不报错，但等于没做）

本 POC 反复出现同一类失败：**命令成功、日志干净、指标为空、结论错**。统一对策：**"新东西上线 = 造一次真实条件看它动"**。

| # | 静默失效现象 | 为什么看不出来 | 验收方式（必须做） | 出处 |
|---|---|---|---|---|
| 1 | 跨源 `A and B` 规则永远 `inactive` | `promtool check rules` 通过、UI 无报错 | 造条件 → `pending → firing` → 还原 | `alerting/README.md` |

| 7 | 对账"假修复"循环 | 对账任务显示成功 | 用正确端点（读 `edge` 键）+ 验证边真在 OM | `AGENTS.md` §7 |
| 8 | Ollama 超长 prompt 被截断 | 有回答、无报错 | 显式 `num_ctx` + 预算口径 = 整条 prompt | `AGENTS.md` §7 |

## 6. Git 入库与脱敏（2026-09-21，本批新增经验）

**事故经过**：首次把仓库推到 GitHub 时，发现 **6 份文档含服务器公网 IP / 主机名共 12 处**，不得不**重写历史 + force-push** 才清掉；随后经 API 实测 GitHub 仓库 `visibility=public`，且**重写前的旧提交对象仍能从远端按 SHA 拉取**（`git fetch origin <旧SHA>` 成功）。

| 经验 | 定式做法 |
|---|---|
| **脱敏必须在首次 push 之前完成** | 首次 push 前跑全量自检（`bash tools/pre_push_scan.sh --all`）；把"人肉检查"固化成**可执行断言**成本最低 |
| **公网 IP / 主机名与口令同级** | 一律用占位符 `<POC服务器公网IP>` / `<POC服务器主机名>`；域名、账号、token 同理 |
| **推送之后改历史仍有残留** | 重写 + force-push **不清远端旧对象**（未被 GC）⇒ 真正的处置是①仓库设 **private** / 删除重建；②请 GitHub Support 触发 GC；改完**复核 `git fetch origin <旧SHA>` 必须失败** |
| **可见性要主动核实，不能假设** | 用 API 查 `visibility`；不要把"我建的是私有库"当前提 |
| **自检脚本的纪律** | 命中时**只报 `文件:行号 + 规则名`、不打印命中内容**（否则等于把密文又写进日志/终端历史）；误报用 `git commit --no-verify` 并在提交信息说明；**改规则后必须自测**（干净文件通过 / 含公网 IP 被拦 / `PGPASSWORD="$PG_PASSWORD"` 这类变量引用不得误报） |
| **本地口令清单放仓库外** | 已知口令字面量清单放 `~/.ai-datathink/secret-patterns.local`，**永不入库** |
| **口令"从未入库"不等于安全** | 曾在会话/终端出现过的口令，建议整批轮换 |
| **仓库是唯一真相源** | 服务器侧脚本/配置改动必须回写仓库（2026-09-21 已因漂移补过 **9 个脚本**）；脚本保持 **LF** |

> **当前挂账（未闭环，需人工）**：仓库可见性仍为 public，且旧提交对象仍可按 SHA 拉取 ⇒ 见 `AGENTS.md` §9 与 `交付物/00_交付物清单.md` §4 第 14 项。

## 7. 下次接手 / 交付前检查清单

**每次改动（通用）**

1. 先读源文档对应章节，确认口径与影响链（`设计方案 → 执行计划 → 部署步骤 → 记录`）。
2. 一次一个主题；改上层必须说明下层是否同步。
3. 证据三件套：命令 + 实际输出 + 判读；跑不了就写原因。
4. 追加版本记录，并同步 `AGENTS.md` §1 地图（新增文件/目录时）。

**改镜像 / 依赖时**

5. 基础镜像钉 digest、依赖钉版本；构建后**取新 digest 并重新钉**。
6. 构建后**重扫**（`--skip-db-update`）并比对 HIGH/CRIT；不得声称"重建即修复"。
7. 跑一次**功能验证**（不只看容器 healthy），确认新代码确实进了镜像。

**改规则 / 采集 / 策略时**

8. 规则：`promtool check rules` → `POST /-/reload` → 查 `/api/v1/rules` `health=ok` → **真实触发验证**。
9. 采集：原子写入 + 逐行自检 + 独立文件 + 单生产者 + `count<预期` 护栏。
10. 策略：编译通过 ≠ 逻辑正确（Rego 冲突运行期表现为 `undefined`）⇒ **必须重跑决策用例**；OPA / Presidio 改完须重启对应容器。

**改权限 / 数据时**

11. 新建库必须做**库级 CONNECT 收敛**；权限变更后必须回收 PgBouncer 池连接并**反向复验**。
12. 临时对象（库/表/Topic/索引/实体）**用完即清并断言零残留**。

**提交 / 交付前**

13. `bash tools/pre_push_scan.sh --all` 通过；确认无真实口令、token、公网 IP、主机名、连接串。
14. 核对"已完成 / 未做 / 待人工"三张清单是否一致（尤其门禁、签字、风险接受**属人工专属**）。
15. 对外下结论前自问一句：**这事我真看到它动了吗？**（§3 的 12 条静默失效）
