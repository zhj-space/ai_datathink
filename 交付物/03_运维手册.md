## 2. 日常巡检（照抄即可）

### 2.1 每天 5 分钟

```bash
# 1) 容器健康
docker compose -f /data/ai-governance/docker-compose.yml ps --format '{{.Name}}\t{{.Status}}' | sort

# 2) 是否有活动告警（应为空）
docker exec ai-governance-poc-prometheus-1 wget -qO- 'http://localhost:9090/api/v1/alerts' | jq -c '[.data.alerts[]?|.labels.alertname]'
docker exec ai-governance-poc-alertmanager-1 wget -qO- 'http://localhost:9093/api/v2/alerts' | jq -c '[.[]?|.labels.alertname]'

# 3) 抓取目标是否全 up（应为 7/7）
docker exec ai-governance-poc-prometheus-1 wget -qO- 'http://localhost:9090/api/v1/targets?state=active' \
  | jq -r '[.data.activeTargets[]|select(.health=="up")]|length as $u|"up=\($u)/\(.data.activeTargets|length)"'

# 4) 三类采集器是否在跑（每 1~5 分钟刷新）
ls -la --time-style=+%H:%M:%S /var/lib/node_exporter/textfile/

# 5) 磁盘余量（加盘阈值：可用 < 20 GiB）
df -h / /data

# 6) 今日告警日报（08:30 生成）
ls -1t /data/ai-governance/reports/alert-digest-*.md | head -1
```

### 2.2 每周 15 分钟

```bash
# 1) 备份成功戳是否新鲜（PG/OS/配置/ETL/RAG/对账）
grep -E '^ai_governance_job_last_success_timestamp_seconds' /var/lib/node_exporter/textfile/ai_governance_jobs.prom

# 2) 备份文件与保留期（14 天滚动）
ls -1t /data/backup/pg/*.dump | head -3
ls -1t /data/backup/config/config_*.tar.gz | head -3

# 3) 复制槽水位（仅接源后有槽；本环境平台自身无槽）
docker exec ai-governance-poc-postgres-1 psql -U postgres -c \
  "SELECT slot_name, pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained FROM pg_replication_slots;"

# 4) 水位周报（周一 08:00 自动；<14 天数据一律"数据不足"，不得据此下结论）
ls -1t /data/ai-governance/reports/watermark-*.md | head -1

# 5) 镜像与构建缓存占用（回收前先确认无容器引用）
docker system df; docker images -a --format '{{.ID}}\t{{.Repository}}:{{.Tag}}\t{{.Size}}\t{{.Containers}}'
```

## 3. 告警体系与处置（40 条规则）

> 通知现状：Alertmanager 的接收端指向 **GA `/api/v1/alerts/ingest`**，告警落库到 `ga.alert_event`；**每日 08:30 生成告警日报**。
> ⚠️ **IM/Webhook 地址尚未提供** ⇒ 目前**没有主动通知到人**，别把"没收到消息"理解为"没有告警"。**值班请以 Prometheus/AM 页面 + 日报为准**。

| 组 | 规则数 | 代表规则 | 级别 | 处置要点 |
|---|---|---|---|---|
| `poc-slo` | 4 | 宿主 CPU>80%、内存>85%、磁盘>85%、**可用 <20GiB** | warning / **critical**（磁盘） | 磁盘类先做无损回收（镜像/缓存/日志），仍不足则加盘并迁 `/data` |
| `postgres-replication-slot` | 5 | **未设兜底**、水位 >兜底 70%、无消费者持有 WAL、**已失效**、超兜底 | critical | 按 ADR-A2 第 2 件处置；**删槽必须走"作业下线 checklist"**，不得随手删 |
| `kafka-lag` | 3 | lag 持续增长 5m、broker 不可用、**exporter 抓取失败** | warning / critical | 单节点无冗余：broker 挂 = 实时链路中断；`lag=-1` 是"取不到偏移"，不是"没滞后" |
| `flink-jobs` | 5 | 抓取失败、**登记了作业但没在跑**、作业重启、**Checkpoint 失败**、Checkpoint 停摆 | warning / critical | Checkpoint 失败 = **恢复能力受损**；先查 `state.checkpoints.dir` 可写性与背压 |
| `job-freshness` | 10 | PG/OS/配置备份过期、ETL/RAG/对账过期、出机过期、**采集器自身停摆**、指标整体缺失 | warning / critical | 备份类过期直接影响 **RPO ≤1h 承诺**；先看 `/data/backup/log/` |
| `ollama-runtime` | 7 | API 不可达、CPU 饱和、内存高、**OOM kill**、模型不卸载、探针停摆、指标缺失 | critical / warning | AI 能力面；OOM/不可达优先，模型不卸载查调用方 `keep_alive` |
| `container-runtime` | 6 | 指标缺失、探针停摆、**序列数不足**、**OOM kill**、内存近上限、CPU 持续饱和 | critical / warning | 单机无冗余：容器被打穿会拖慢同机其它组件（实时链路优先） |

**处置三步（对任何告警都适用）**：
1. **先留证据**：`查 Prometheus/AM 页面` + `ga.alert_event` 里的 `enhanced_summary`（GA 会按规则名给处置建议）
2. **再按上表处置**；涉及**删除/降级/改架构**的动作 —— **停手转人工**
3. **复盘**：把"现象 / 根因 / 处置 / 结果"补进对应记录文档的版本记录

## 4. 备份与恢复

| 对象 | 频率 | 位置 | 判据 |
|---|---|---|---|
| PostgreSQL（6 库逻辑备份） | 每小时 `:05` | `/data/backup/pg/*.dump` | 最新 mtime 新鲜；**RPO ≤1h** |
| OpenSearch 快照 | 每小时 `:15` | `/data/opensearch/snapshots` | 快照目录最新条目新鲜 |
| 配置归档（`.env`+compose+`config/`） | 每日 `02:55` | `/data/backup/config/config_*.tar.gz`（600，14 天滚动） | **含密钥**，恢复时**必须一起恢复** |
| 出机（异地） | 每日 `03:00` | 异地介质 | ⏳ **本环境暂缓** ⇒ 备份仍在同一故障域 |
| 保留期 | 14 天滚动 | —— | 超期自动删除 |

**恢复演练（已做过的两项）**：
- **逐库恢复演练**：6 库恢复一致、单库 ≤2.6s
- **年度化恢复演练（本地段）**：PG 6 库一致、OpenSearch 快照一致、配置归档**密钥键名 24/24**、对象级合计 8s
  - ⚠️ 报告固定声明 5 条未覆盖（PG PITR / Flink CP 出机恢复 / 出机副本恢复 / 主机级重建 RTO / 真实业务量恢复）
  - ⚠️ **PG PITR 在本环境不存在**（未启用 WAL 归档）⇒ **不得把 dump 恢复说成 PITR**

**恢复操作要点**：
1. 配置归档**含真实密钥** ⇒ 解包到 `/tmp`、用毕即删、**删除前断言路径前缀**
2. `DROP DATABASE` 前必须 **`RECONNECT` 回收 PgBouncer 池连接**（活动连接会挡住 DROP）
3. 恢复后**必须重跑该组件验收**（健康 + 读指标 + 反向权限）
4. **判读属人工**：恢复演练结论由人工确认，Agent 只给证据

## 7. 已知缺口与限制（运维必须知道）

| # | 缺口 | 影响 | 临时对策 |
|---|---|---|---|
| 1 | **IM/Webhook 未配** | 告警**无主动通知** | 以页面 + 日报为准；地址到位后在 AM route 加 receiver（Prometheus 侧不用改） |
| 2 | **cAdvisor 逐容器指标不可用**（containerd 镜像存储 vs v0.45；镜像源被拦） | 容器级 CPU/内存/OOM 不可见（若只看 cAdvisor） | **已由自采探针 `container_probe.sh` 覆盖**；cAdvisor 记外部阻塞 |
| 3 | **OM 采集运行状态未回写** | OM UI 看不到本次运行成功/失败 | 以 Airflow 任务日志判定 |
| 4 | `airflow dags list-runs` 报 `Database migration required` | 仅容器内 CLI 不可用 | 用 Airflow UI / REST API |
| 5 | 出机介质暂缓 | 备份仍在同一故障域（门禁② 该项挂账） | 尽快恢复出机流程 |
| 6 | 未接真实业务源 | 资产仅 1 个、血缘与覆盖率无业务数据 | 接源当天按《接源前检查清单》执行（**先确认门禁④ 原件已归档**） |
| 7 | 水位周报首个可判定报告 ≈ 2026-10-05 | 现在所有水位判定都是"数据不足" | 不要提前下结论 |

## 8. 停机 / 变更 / 删除的红线

1. **不自动降级、不自行改架构**：遇 `unhealthy` 先记录日志、停止操作、转人工（AGENTS 硬约束 5）
2. **删除类操作先确认**：删复制槽走"作业下线 checklist"；删镜像/数据前确认无引用；`rm -rf`/`DROP` 一律需人工明确要求
3. **接生产库前置**：门禁④ 两份原件归档（硬约束 4）
4. **`wal_level=logical` 变更需重启 PG** ⇒ 属**停机窗口**，必须提前与 DBA 约
5. **不把"能跑"当"已验证"**：任何结论都要有命令 + 输出
