# AI 数据治理平台实施执行计划 v2.0

> **依据**：本计划基于 [AI数据治理平台设计方案.md](./AI数据治理平台设计方案.md)（v3.2，已合入 8 条 ADR 与全部架构调整）拆解而成。架构/组件选型以设计方案 v3.2 为唯一权威来源，本文档不重复贴组件表。
> **与 v1.1 的差异（本章为变更摘要，已按 v1.1 的用户可直接看增量）**：
> 1. 部署形态从"单机默认 / 3 节点备选"升级为**两阶段固定路线**：POC 单机（1 台）→ 生产 3 节点 k3s（触发条件明确，见第 1 章）
> 2. **Phase 0 拆分为 P0-A（采购与外部依赖，并行启动）与 P0-B（单机底座搭建）**——长周期审批（硬件、Kafka、SSO、binlog 签约定）全部提前，不占关键路径
> 3. 新增 **M0 技术实测清单**（6 项待核实风险的前置消解，含 OM × PgBouncer 兼容性实测）
> 4. 追加 **M-Prod 里程碑**（3 节点生产化，触发式启动，含迁移演练）
> 5. 新增 **8 条 ADR → 任务映射表**（第 5 章），每条 ADR 都有落地任务、责任阶段与验收口径
> 6. 外部依赖清单扩充：Kafka topic 申请、binlog 保留期签约定、SSO 对接、合规方边界确认、已有基础设施盘点
>
> **节奏说明**：周数为建议节奏；实际推进以门禁为准——门槛未达标不进入下一阶段，也不因到了预定周数强行推进。
> **执行方说明**：每项任务标注执行方（Agent 自主执行 / Agent 起草+人工审核 / 人工专属），边界见第 8 章，不可越界自动化。

## 1. 总体路线（两阶段形态）

```
阶段一：POC（单机，1 台 24C/96G/2TB，Docker Compose，约 17 容器）
┌─────────────────────────────────────────────────────────────┐
│ P0-A 采购与外部依赖（并行，不占关键路径）                       │
│ P0-B 单机底座（2~3 周）→ Phase 1 离线闭环（3~4 周）             │
│ → Phase 2 实时链路（3~4 周）→ Phase 3 AI 能力（3~4 周）        │
│ → Phase 4 试运行与生产化评估（2~3 周）                          │
│ POC 合计约 11~14 周                                            │
└─────────────────────────────────────────────────────────────┘
                          │ 满足任一触发条件
                          ▼
阶段二：生产（3 节点 k3s，触发式启动 M-Prod，4~6 周）
┌─────────────────────────────────────────────────────────────┐
│ M-Prod：3 台采购（按 ADR-A8 公式）→ k3s+VIP+MetalLB+CNPG        │
│ + SeaweedFS（必需）→ 状态服务迁移演练 → 切流                     │
└─────────────────────────────────────────────────────────────┘
```

**M-Prod 触发条件（满足任一即启动评估，决策人 ARCH+PM）**：

| # | 触发信号 | 判定方式 |
|---|---|---|
| 1 | 业务要求 SLA 超出单机能力（单点故障不可接受） | 业务方书面提出 |
| 2 | 单机资源水位持续 >70%（CPU/内存/磁盘任一） | Prometheus 周报连续 2 周超标 |
| 3 | 数据规模超出单机档容量（详见 ADR-A8） | 接入数据源规划评审 |
| 4 | 合规要求明确生产级高可用 | SEC 转达监管/内审要求 |

**未触发前的纪律**：不预购 3 台服务器、不预装 k3s、不为"将来迁移"做提前适配——单机档所有配置以 Compose 可运行为准，迁移能力由 M-Prod 阶段的迁移演练保证，而不是靠提前设计。

## 3. 资源需求

### 3.1 硬件（两阶段分批到位）

| 资源项 | 规格建议 | 到位时点 | 备注 |
|---|---|---|---|
| POC 单机 ×1 | 24 vCPU / 96GB / 2TB（数据盘 SSD），参考设计方案中型档 | P0-B 启动前 | **只买 1 台**；容器内存 limits 之和 ≤ 70%（约 67G） |
| 生产节点 ×3 | 按 ADR-A8 公式测算：`每节点 = PG全量×1.3 + 日增×Kafka保留天数 + OS索引(<100GB) + Checkpoint + 系统盘480G + 20%余量`；短保留方案 4TB/节点（预算紧时推荐），长保留 8TB/节点 | M-Prod 启动后 | 三台规格一致；**仅在触发条件满足后才采购** |
| 对象存储 | SeaweedFS 自建（3 节点形态必需，M-Prod 阶段部署）或复用企业已有 MinIO/云 OSS | M-Prod | POC 期 Flink Checkpoint 落本地盘 + 每日出机备份（ADR-A4） |
| GPU（可选） | 单卡，按模型规模评估 | Phase 3 按需 | 仅当 CPU 推理无法满足 SLO（流式首 token <10s）时引入 |

### 3.3 成本构成要素

沿用 v1.1：纯开源无许可费；主要成本 = 硬件（POC 1 台 + 生产触发后 3 台，**分两批投入**）+ 人力 + 可选 GPU/对象存储。v2.0 的资金优势：POC 期硬件投入从 3 台降为 1 台。

## 4. 分阶段执行计划（周粒度任务分解）

### P0-A：采购与外部依赖（建议 2 周，与 P0-B 并行，不在关键路径）

| 周 | 任务 | 负责人 | 执行方 |
|---|---|---|---|
| 第1周 | POC 服务器采购流程发起；已有基础设施盘点（Kafka/SSO/备份/监控四项清单输出） | PM、INFRA | 盘点表起草为 Agent 起草+人工审核（资产归属与可用性必须人工确认）；采购流程为人工专属 |
| 第1周 | binlog 签约定预沟通（把"≥3×停机预算"的公式和监控需求带给 DBA）；源库 CDC 权限评估发起 | DBA | 人工专属（跨组织约定） |
| 第2周 | 合规方边界确认发起（书面文件起草：POC 期事后审计定位）；SSO/Kafka 接入申请提交 | SEC、INFRA | 文件起草为 Agent 起草+人工审核；提交与跟进为人工专属 |

**准出门槛**：采购流程已进入流转；基础设施盘点表已输出并被 PM 确认；三项申请（CDC 权限/SSO/Kafka）均已提交。**P0-A 未完成不阻塞 P0-B 启动，但阻塞 Phase 1/2 的对应任务。**

### P0-B：单机底座搭建（建议 2~3 周）

| 周 | 任务 | 负责人 | 执行方 |
|---|---|---|---|
| 第1周 | 服务器到位、OS/网络/数据盘配置；Docker + Docker Compose 安装；目录规划（`/data` 挂独立数据盘）与三网隔离（前端网/后端网/数据网） | INFRA | 到位/网络为人工专属；安装与配置脚本为 Agent 自主执行 |
| 第2周 | 部署 PostgreSQL+pgvector、**PgBouncer**（transaction 模式起配）、OpenSearch；PG `max_connections` 收至 60~80，省出内存给 `shared_buffers`/`effective_cache_size` | INFRA、DBA | Agent 自主执行（compose 产出部署报告供人工审阅） |
| 第3周 | Prometheus + Alertmanager 容器上线（采集所有容器 + 宿主机）；Traefik 入口 + TLS 验证；备份脚本（PG 逻辑备份 + OpenSearch snapshot + Flink Checkpoint 目录每日出机）并完成**一次恢复演练** | INFRA、DBA、QA | 部署与脚本为 Agent 自主执行；恢复演练结果验证为人工专属（DBA 签字） |

**准出门槛**：所有基础容器健康检查通过；备份脚本验证可恢复（**RPO≤1h** / RTO≤4h 的演练记录）；PgBouncer `SHOW POOLS` 无 waiting 堆积。

> **RPO 口径回填（2026-09-17 人工决策）**：原写「RPO≤15min」与设计方案 4.6「≤1 小时」冲突。经 PM 决策，**采用设计方案 4.6 的 ≤1h**：
> 单机 POC 形态下由**小时级 PG 逻辑备份**（+ OpenSearch snapshot + Flink Checkpoint 出机）承接；分钟级手段（WAL 归档 PITR）**不引入**——如需收窄到 ≤15min，属口径变更，须走 ADR 流程。

**关键决策点**：PgBouncer 池化模式选定（见 M0 实测清单第 1 项，决策人：DBA+DE）。

### M0 技术实测清单（P0-B 第 3 周起并行，Phase 1 第 1 周收尾）

此前评估挂账的 6 项待核实风险，全部在此前置消解，**每项都有明确回退路径**：

| # | 实测项 | 方法 | 通过标准 | 回退路径 |
|---|---|---|---|---|
| 1 | **OM × PgBouncer transaction 兼容性** | OM 全链路过池：登录→浏览→跑一次 ingestion→血缘/质量页 | 无 `prepared statement does not exist`、无事务外操作报错 | transaction → session → 直连（改一个配置项，成本≈0） |
| 2 | Flink CDC 版本矩阵 | connector 与 Flink/PG/MySQL 版本组合实测；涉及 Oracle 需核实 LogMiner/XStream 授权；**PG 源库复制槽行为验证**（停作业观察 WAL 回收是否停止、`max_slot_wal_keep_size` 兜底是否生效） | 试点源库类型全部捕获正常；PG 场景 slot 行为符合 ADR-A2 第 2 件预期 | 锁定已验证组合，写进部署基线 |
| 3 | 无主键表增量行为 | 选 1 张无主键业务表做快照+增量 | 能捕获且不重复/不丢失 | 该类表改用全量轮询或补主键 |
| 4 | DDL/Schema Evolution | 加列/改类型场景各测一次 | 行为可预期（报错或自适应） | 冻结 schema 变更流程，DDL 走人工窗口 |
| 5 | 镜像供应链 | 自建 Flink CDC 镜像固定 digest + 扫描 | 扫描无高危漏洞 | 换基镜像重建 |
| 6 | Ollama CPU 推理 SLO | Qwen 目标模型流式首 token 计时 | <10s（设计方案 SLO） | 量化版换小模型 / Phase 3 申请 GPU |

| 周 | 任务 | 负责人 | 执行方 |

| 第3周 | Presidio 批量扫描规则配置（含中国证件自定义识别器）；置信度分层调优；OPA 基础访问策略编写（Rego 入 Git）；**gov_metrics schema 建立 + Governance Agent 指标 ETL 首版**（ADR-A6，约 3~5 人天） | DE、SEC、GOV | 规则与策略均为 Agent 起草+人工审核；ETL 开发为 Agent 自主执行 |

**关键决策点**：① Presidio 规则抽检准确率是否达标（SEC+GOV）；② 场景 E 边界确认是否已拿到合规方书面文件（**未拿到不得进入 Phase 2 实时链路对生产库的接入**）。
**准出门槛**：试点源资产目录覆盖率 100%；PII 抽检准确率 >90%；血缘 Top 50 列级抽检 ≥90%；Superset 全部查询落在 gov_metrics；合规边界文件归档。

### Phase 2：实时链路引入（建议 3~4 周）

| 周 | 任务 | 负责人 | 执行方 |
|---|---|---|---|
| 第1周 | **续接窗口签约定收口**（ADR-A2 四件套第 1 件，未签订不动生产库）；**PG 源库复制槽安全保护配置**（第 2 件：`max_slot_wal_keep_size` 兜底 + slot 水位最高级告警）；Flink CDC 直连接入试点业务库；Kafka topic 规划（`governance.alerts` + 日志事件；若复用企业集群，用 P0-A 申请的 topic） | DBA、DE | CDC 接入生产源库为 Agent 起草配置+DBA 审批后执行；slot 保护参数为 Agent 起草+DBA 审核后执行；topic 规划为 Agent 自主执行 |
| 第2周 | Flink 作业开发：CDC Source（快照+增量）+ 窗口规则引擎 + **作业图级血缘上报**（表述已按 ADR-A7 修正）；**质量口径拆分落地**（ADR-A5：快照基线→OM 质量测试；增量窗口命中→governance.alerts 告警，不进质量看板） | DE、ARCH | 作业开发部署为 Agent 自主执行；规则逻辑上线前人工审核 |
| 第3周 | 作业自动拉起落地（ADR-A2 第 2 件：`restart: unless-stopped` + healthcheck + Checkpoint 成功率最高级告警）；Governance Agent 告警增强模块；Alertmanager/IM 打通 | DE | Agent 自主执行 |
| 第4周 | **CDC 断流恢复演练**（停机 ≤ binlog 保留期 1/3 内恢复、无重新快照）；**重快照预案演练**（ADR-A2 第 3 件：大表限速、低峰、跳非关键表）；端到端压测 P95 | QA、DE、DBA | 演练脚本与采集为 Agent 自主执行；结果判读与源库负载评估为人工专属（DBA 签字） |

**关键决策点**：① CDC 对源库负载是否可接受（DBA+源系统负责人签字）；② **两段式切换信号初评**（ADR-A1：是否已有其他 CDC 消费方、背压是否持续告警——若有，本阶段末即启用 Flink CDC→Kafka→处理的两段式）。
**准出门槛**：端到端延迟 P95 <30s；断流恢复（≤ 续接窗口 1/3）与重快照演练通过；PG 复制槽保护验证通过（兜底生效 + 告警触发 + 作业下线删 slot 演练）；质量看板无增量窗口数据混入；连续运行 1 周无未恢复故障。

### Phase 3：AI 能力增强（建议 3~4 周）

| 周 | 任务 | 负责人 | 执行方 |
|---|---|---|---|
| 第1周 | Ollama+Qwen 部署（CPU 起步，M0 实测第 6 项不达标则触发 GPU 评估）；嵌入模型选型验证（BGE-M3 / nomic-embed-text） | AI | Agent 自主执行 |

## 8. Agent 执行边界与安全护栏

沿用 v1.1 第 7 章全部条款（可自主执行 / 必须暂停等确认 / 前置条件 / 人机协作节奏），v2.0 增补两条：

- **单机档纪律**：Agent 不得在 POC 期擅自引入 K8s 相关配置"为将来做准备"（违反第 1 章"未触发前的纪律"）；Compose 文件是 POC 期唯一部署真相源。
- **M-Prod 切流期纪律**：切流窗口内所有操作从"Agent 起草+人工审核"升级为"Agent 起草+人工逐步放行"（每一步执行前人工确认）；回滚触发权归 PM，Agent 发现异常只上报建议，不得自行回滚。

## 9. 沟通与汇报机制

沿用 v1.1 第 6 章（周例会 / 阶段门禁评审会 / 月度汇报），v2.0 增补：

- **单机水位周报**（Phase 4 起，INFRA 出，Agent 生成）：CPU/内存/磁盘水位 + 趋势，直接对照 M-Prod 触发条件 2——让"要不要上 3 节点"的讨论永远基于数据而非感觉。
- **试运行 90 天三问**月报：周活用户数、识别准确率是否稳在验收线上、告警处置率（对齐 v3.1 运营模型）。

## 10. Agent 任务卡示例（v2.0 更新为单机版 + M-Prod 版）

### 任务卡 P0-B-1：单机基础底座部署

- **前置条件**：POC 服务器到位、SSH 可达、数据盘已挂载（人工确认后触发）
- **输入**：服务器 IP/主机名、数据盘路径、基础设施盘点表中确认复用的外部地址（Kafka/SSO）
- **执行步骤**：① 编写 docker-compose（PG+pgvector / PgBouncer / OpenSearch / Prometheus / Alertmanager / Traefik，三网隔离，全部 `restart: unless-stopped` + healthcheck）；② `docker compose up -d`；③ 健康检查脚本验证
- **验收标准（可编程校验）**：`docker compose ps` 全部 healthy；PgBouncer `SHOW POOLS` 可查询且无 waiting；Prometheus 抓到全部容器指标
- **失败处理**：任一容器 unhealthy，记录日志停止，重试 ≤3 次转人工
- **人工确认点**：部署报告审阅后继续下一任务卡

### 任务卡 T-M0-1：OM × PgBouncer transaction 兼容性实测

- **前置条件**：P0-B-1 完成；OM 部署完成且连接串指向 PgBouncer
- **执行步骤**：① OM 登录、浏览元数据、搜索（触发 OpenSearch 链路）；② 跑一次完整 ingestion；③ 打开血缘与质量页面；④ 收集 PgBouncer 日志与 OM server 日志中的报错
- **验收标准（可编程校验）**：日志零命中 `prepared statement .* does not exist` / `transaction aborted` 类错误
- **失败处理**：**不自动降级**——输出失败证据包（日志+复现步骤），由 DBA+DE 决策走 session 还是直连
- **人工确认点**：实测结论写入部署基线文档后，PgBouncer 配置定版

### 任务卡 M-PROD-1：k3s 三节点集群搭建

- **前置条件**：M-Prod 触发评审通过、3 台服务器到位（人工确认后触发）
- **执行步骤**：① 第一台 `k3s server --cluster-init`；② 其余两台 join；③ kube-vip 部署（API Server VIP）；④ 安装 MetalLB 前**先禁用 Klipper**；⑤ `kubectl get nodes` 验证
- **验收标准（可编程校验）**：3 节点 Ready；VIP 漂移测试通过（关停持有节点，VIP 30s 内漂移）
- **失败处理**：记录日志停止，转人工排查
- **人工确认点**：集群健康 + VIP 漂移验证人工复核后，方可进入第 3 周 CNPG/OpenSearch 部署
